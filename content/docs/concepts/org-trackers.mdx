title: Org-level trackers
description: One beacon embedded across several domains, routed to a site per domain. When to use it, and how routing and discovery work.

A [site](/en/concepts/sites) is one property with its own beacon. An **org-level tracker** is one beacon you embed across **several domains that share a codebase**, so you maintain a single snippet instead of one per domain. The classic case: country shops on `shop.de`, `shop.fr`, `shop.it` built from the same frontend.

The tracker's `collector_hash` resolves the right site at ingest, from the page's own hostname, so each domain still lands on its **own site**, with its own analytics and configuration. You get one embed and separate per-domain reporting.

## When to use one

- **Several domains, one codebase.** Country or brand shops, or a multi-region deployment, where embedding a separate snippet on each would be a maintenance drag.
- **You still want per-domain analytics.** Each registered domain reports separately; the org tracker is only the delivery mechanism.

Use a plain [site](/en/concepts/sites) tracker instead when a property stands alone, or when you need **different collection behavior per domain** (see below).

## How routing works

Every beacon carries the page URL. At ingest the collector reads the **hostname** from that URL and matches it against your organization's sites:

- **Exact hostname match.** `Site.domain` must equal the observed hostname. `shop.de` matches the site `shop.de`; `www.shop.de` or `de.shop.com` do **not** match a site registered as `shop.de`. Register each domain you serve as its own site.
- **Matched:** the beacon lands on that site, stamped with its `site_id`, exactly as a per-site tracker would.
- **No match:** the hostname is recorded for [discovery](#discovery-unknown-hostnames) and the beacon is not written.

So the setup is: provision one org tracker, register each domain as a site, embed the tracker's snippet everywhere.

## Settings are org-wide

An org tracker serves **one bundle** to every domain, so its data-scope and routing [tracker settings](/en/tracker) (`store_session`, `preconsent_level`, `store_error_messages`, `error_frame_detail`, `track_query_keys`, `query_value_keys`, `fetch_xhr_enabled`, `collector_mode`, `collector_endpoint`) apply **the same to every domain**. It takes the same [presets](/en/tracker#presets).

Three settings stay **per site**, resolved on the matched site at ingest:

- [`store_stitch`](/en/tracker#store-stitch), enforced per site when the row is written,
- [`preferred_identity`](/en/tracker#preferred-identity), a per-site reporting default,
- [`enforce_domain_match`](/en/tracker#enforce-domain-match) and [`allowed_origins`](/en/concepts/sites#allowed-origins), the ingest guards, which apply on the resolved site.

If you need genuinely different collection behavior per domain (say, session tracking on one shop but not another), that's the signal to give that domain its own per-site tracker instead.

## Visitors across domains

The edge-derived [`stitch`](/en/tracker#store-stitch) includes the page **domain** in its input, so the same visitor on `shop.de` and on `shop.fr` gets a **different** `stitch` on each. An org tracker counts each domain's visitors separately; it does not unify a visitor across the domains. It is a delivery-and-routing convenience (one embed, one site per domain), not a cross-domain identity. Everything else about `stitch` (bounded ≤24 h joinability, forward secrecy, nothing stored on the device) is unchanged; see [Privacy → the edge-derived `stitch`](/en/privacy#the-edge-derived-stitch-identifier).

## Discovery: unknown hostnames

When the tracker reports a hostname that matches no registered site, fastmon doesn't silently drop it: it **counts it and surfaces it as a suggestion**, so you can add the missing domain as a site. This catches a new country shop, or a forgotten staging domain that's already carrying the snippet. Suggestions live for about a week and are capped per organization; dismiss the ones you don't want. Until a hostname is registered as a site, its beacons are not written.

## What's on an org tracker

| Field | Notes |
| --- | --- |
| `id` | UUID v7. |
| `organization_id` | The owning organization. An org can have more than one tracker. |
| `name` | Label, shown in the dashboard. |
| `source_hash` | Per-tracker hash in the script URL (`/s/{source_hash}.js`). |
| `collector_hash` | Per-tracker hash in the ingest URL (`/c/{collector_hash}`), and the edge stitch anchor. |
| data-scope + routing settings | `store_session`, `preconsent_level`, `store_error_messages`, `error_frame_detail`, `track_query_keys`, `query_value_keys`, `fetch_xhr_enabled`, `collector_mode`, `collector_endpoint`. Baked into the served bundle, org-wide. See [Tracker settings](/en/tracker). |
| `source_version` | Pins the beacon template version. |
| `is_active` | When false, beacons are accepted but not written. |

`store_stitch`, `preferred_identity`, and `enforce_domain_match` are **not** on the tracker; they live on each resolved site.

## `domain` vs. `hostname`

Two related terms, kept distinct on purpose:

- **`domain`** is the value you configure on a site (`Site.domain`, in the API, the dashboard, and reports). It doesn't change.
- **`hostname`** is what the tracker observes: the host parsed from the page URL at ingest. Org-tracker routing and discovery match on the hostname.
