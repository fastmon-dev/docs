The **beacon** is the JavaScript file Fastmon serves at
`https://fastmon.site/s/{source_hash}.js`. That's the only
client-side code we ship, and the only thing your visitors load
from us.

This page is the technical reference. For setup, head to
[Implementation](/en/install); for the privacy posture, see
[Privacy: what we don't collect](/en/privacy).

## Two builds, one URL

The `<script>` tag always points at the same URL, but the bytes
underneath are one of two builds, chosen by the application's
`collect_sessions` setting:

| Build | When | On-device storage |
|---|---|:---:|
| `stateless.js` | `collect_sessions` off (`minimal`, `standard`) | None — the session-id code is compiled out entirely |
| `stateful.js` | `collect_sessions` on (`full`) | One `sessionStorage` entry (`_fms`), no cookies |

You don't pick the build in the `<script>` tag; the server resolves
it from the application's config and ships the right one. Neither
build sets a cookie — the only difference is whether the
`sessionStorage` session-id code is present at all. Changing the
[preset](/en/collection-modes) rolls the script cache automatically.

## Why it matters

The beacon is the boundary between Fastmon and the visitor.
Whatever happens here (what's measured, when it flushes, which
identifiers get minted) the browser sees, and anyone reading the
script can see it too. So we keep the surface small on purpose:
small means auditable, quick to load, and easy to defend in a
privacy review.

## What the beacon observes

| Source                     | What's captured                                                                |
| -------------------------- | ------------------------------------------------------------------------------ |
| `PerformanceObserver`      | LCP, INP, CLS, FCP, paint entries, long animation frames, layout shifts.       |
| `Navigation Timing`        | TTFB, redirect count, navigation type (`navigate`, `reload`, `back_forward`).  |
| `Resource Timing`          | Per-resource size, duration, and category. Aggregated to per-domain rollups.   |
| `error` event              | Type, count, and stack-frame hosts in every preset. `standard` / `full` add each frame's path + line/column (`collect_error_frames`); `full` also keeps the error message (`collect_error_messages`), after an always-on PII scrubber masks URLs, emails, IDs, and quoted strings. |
| `unhandledrejection`       | Same shape as `error`.                                                         |
| `Page Visibility API`      | Time-to-hidden, total visible time.                                            |
| Document & Window          | Page URL (sanitized per [preset](/en/collection-modes)), referrer, viewport size class. |

Geo data (the country) is **not** read in the browser. The
edge derives it from the request IP and forwards a country code as
a `FM-Country` header; the IP itself never reaches the application.
Same for the bucketed browser / OS / device family, forwarded as
`FM-Browser` / `FM-Browser-Version` / `FM-OS` / `FM-Device` — these
are added at the edge, not sent by the beacon. The edge also
computes a one-way `FM-Stitch` header
(`HMAC-SHA256(rotating-24h-salt, IP | UA | collector_hash)`
truncated to 128 bits) that the backend uses for bounded
cross-pageview joins (whenever `store_stitch` is on). See
[Privacy → The edge-derived `stitch` identifier](/en/privacy#the-edge-derived-stitch-identifier)
for the legal framing. The beacon itself never asks for
geolocation.

## What the beacon does not do

- Read or write `localStorage` / `IndexedDB` / `Cache Storage` in
  either build.
- Set cookies — ever, in either build. The only device write is the
  `sessionStorage` session id, and only under `full`.
- Read URL query values or hash fragments (it keeps bare query key
  names only when `collect_query_keys` is on).
- Touch DOM content (no scroll-replay, no session-replay, no form
  capture).
- Read the visitor's media devices, sensors, or geolocation.
- Mint a cross-pageview identifier on the device unless `full`
  stores a session id. The per-pageview `pvid` exists always and
  dies with the pageview; the `stitch` is computed server-side at
  the edge, never on the device.

## The lifecycle of a pageview

```
page loads
  ├── beacon script downloads (defer, cached, ETag-validated)
  ├── tracker registers PerformanceObserver and event listeners
  ├── visitor uses the page
  │     └── tracker accumulates the pageview snapshot in memory
  └── flush triggers (init, loaded, visibilitychange→hidden, pagehide,
      soft-nav, error/fetch-xhr update, or terminate) POST to
      /c/{collector_hash} with a versioned cumulative snapshot
```

Each beacon carries the **full cumulative snapshot** of the pageview
so far (not a batch of discrete events), tagged with a monotonic
`ver`; the server keeps the highest `ver` per `pvid`. The flush uses
`navigator.sendBeacon()` when it's available, so the request
survives even if the page is unloading. If `sendBeacon` isn't
available, the tracker falls back to `fetch` with `keepalive: true`.
If *both* fail (legacy browsers, very aggressive extension
blocking), it falls back to a GET pixel at
`/c/{collector_hash}.gif?…`. That URL serializes a safe subset of
fields into the query string. Sensitive payloads (`sid`, referrer,
errors, the large third-party / resource-breakdown / LoAF JSON
blobs) are excluded from the pixel fallback by name (`PIXEL_SKIP_KEYS`),
so they never travel through any access-log surface.

## The wire payload

The payload is JSON with deliberately short keys to keep the wire
size down. The body is capped at 8 KiB. All fields are optional;
a representative envelope looks like:

```json
{
  "sid":  "01HZX...",
  "pvid": "01HZY...",
  "ver":  3,
  "lcy":  "hidden",
  "pst":  1746604800000,
  "cst":  1746604803456,
  "u":    "https://acme.com/pricing",
  "r":    "https://google.com/",
  "vc":   "wide",
  "c":    "4g",
  "ttfb": 320,
  "fcp":  1100,
  "lcp":  1820,
  "inp":  140,
  "cls":  0.05,
  "errs": [ { "t": "TypeError", "n": 1, "m": "...", "fr": "..." } ],
  "tv":   "260508-a1b2c3d",
  "dlv":  "b"
}
```

You don't usually need to read this; the dashboard and the
[Analytics API](/en/api/analytics/queryAnalytics) unpack it for you. It's
documented here for transparency.

Key abbreviations:

- `sid`: session id. Lives in `sessionStorage` under `_fms`. Only
  present under `full` (or a custom preset with `collect_sessions`
  on).
- `pvid`: per-pageview id. New on every pageview, not persisted.
- `ver`: monotonic version of this pageview's cumulative snapshot.
- `lcy`: lifecycle marker — one of `init`, `loaded`, `error_update`,
  `fetch_xhr_update`, `softnav`, `hidden`, `frozen`, `terminated`.
- `pst`: page-started timestamp, visitor wall-clock (ms since epoch).
- `cst`: client-sent-at timestamp, visitor wall-clock at flush.
  Used server-side to detect clock skew against receive time.
- `u`, `r`: page URL and referrer, both pre-sanitized at the
  tracker to origin + pathname (query values and hash dropped; bare
  query key names kept when `collect_query_keys` is on). `r` is
  classified server-side into bucketed source + medium and the
  raw value is dropped before any logging path. It never
  persists, in any preset.
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`,
  `utm_content`, `click_id_param`: campaign attribution
  extracted from `window.location.search`. Each capped at 64
  chars. `click_id_param` is the platform *label* only
  (`"gclid"` / `"fbclid"` / …); the click-ID value is dropped
  by the tracker. Emitted in all presets.
- `vc`, `c`: viewport class and connection type, read in the
  browser. `rtt` / `dl` join the connection group as real-time RTT
  and downlink estimates. Browser / OS / device family are **not**
  in the wire payload — the edge adds them from `FM-*` request
  headers.
- `pre`, `ad`, `vd`: prerender flag (Speculation Rules API),
  activation delta (ms, prerendered pages only), and
  visibility-dirty (was the tab backgrounded during the
  pageview).
- `ttfb`, `fcp`, `lcp`, `inp`, `cls`, `tbt`, …: mnemonic timing
  keys (Web Vitals, cache hit rate, resource breakdowns, LoAF
  aggregates). Older bundles used `tNN` slots; the collector still
  accepts those as aliases.
- `errs`: error entries (`t` type, `n` count, `m` message, `fr`
  frames). `t` and `n` ship in every preset, and so does each
  frame's host. `standard` / `full` add each frame's path and
  line/column (`collect_error_frames`); the message `m` is
  `full`-only (`collect_error_messages`) and even then runs through
  a scrubber that masks URLs, emails, IDs, and quoted strings.
- `tv`: tracker version, format `YYMMDD-<git-sha>[-dirty]`.
- `dlv`: delivery method — `"b"` on the `sendBeacon` path; absent on
  the `fetch` and pixel paths (the server infers those).

## Cache and rollouts

The script is served with strong caching and an `ETag`. Two things
invalidate the cache automatically:

- **Config change.** Switching an application's [preset](/en/collection-modes)
  (or a flag that flips the `stateful`/`stateless` build) ships a
  new template version.
- **Beacon upgrade.** Fastmon ships beacon versions
  (`source_version`); changing an application's pinned version rolls
  the cache.

You don't need to redeploy your site to take a beacon upgrade.
The browser picks up the new version on its next cache check.

## Customer-facing JS API

Two integration points, both namespace-stable across bundle
versions:

### Sample rate (both builds)

```js
// 10% of pageviews are tracked (default 1.0 = 100%)
window.__FASTMON_SAMPLE_RATE = 0.1;
```

Read once per pageview when the tracker resets. Decisions are
per-pageview, not per-beacon: a sampled pageview emits all its
lifecycle beacons; an unsampled one emits none. Allowed range is
`[0, 1]`; out-of-range values are clamped silently. Set this before
the script tag if you want the very first beacon respected.

### Consent — release the session id (`stateful` build)

```js
window.fastmon.grantConsent();   // consent granted: write the session id
```

Only relevant when the application defers the session-id write
(`session_consent = deferred` with `collect_sessions` on). It writes
the `sessionStorage` session id that was held back until now; it is
write-only and idempotent, with **no revoke** (nothing was stored
before consent, so there's nothing to clear). It gates only the
on-device write, never collection — beacons still flow before
consent, with an empty `sid`. `window.__fastmon_consent(true)` is a
deprecated alias. See
[Presets → Gating the session id behind consent](/en/collection-modes#gating-the-session-id-behind-consent).

## Presets

The beacon's runtime behavior depends on the application's
[preset](/en/collection-modes):

- `minimal`: observes and sends with no visitor identifier at all —
  no `sid`, no stored `stitch`, error type + count only.
- `standard` (default): adds the edge-derived `stitch` (unique
  visitors, no device storage), full error stack frames, fetch/XHR
  timing, and query key names. Still no `sid`.
- `full`: adds the `sessionStorage` session id (`sid`) and the error
  message.

The edge-derived `stitch` header is computed for every preset that
keeps it (`store_stitch` on — i.e. not `minimal`); see
[Privacy](/en/privacy#the-edge-derived-stitch-identifier). Preconsent
(`session_consent`) only gates *when* the `sid` is written, never the
rest of the payload. In every preset, the guarantees in
[Privacy](/en/privacy) hold.

## Rate limiting

The collector rate-limits per `(collector_hash, client_ip)`. The IP
is read at the edge for that bucket only; the application sees a
pre-derived bucket key, not the raw IP, and the IP is not written
to disk. It's defensive: a broken page or a synthetic load test
shouldn't saturate ingestion for other tenants. Real traffic
basically never hits it.

A rate-limited beacon gets a `429`. The browser drops its buffer
and carries on; nothing else breaks.

Payloads larger than 8 KiB return `413`. If `cst` is more than 5
minutes off the server clock, the server falls back to its own
receive time instead of rejecting; the beacon is still accepted.

## Things worth knowing

- **SPA route changes start a new pageview.** The script stays
  loaded, but soft-navs (patched `history.pushState` + `popstate`)
  mint a new `pvid`, reset the Web-Vitals observers, and flush a
  `softnav` beacon for the previous pageview. So one tab can emit
  many pageviews.
- **Multiple flushes per pageview.** The snapshot flushes on
  lifecycle triggers (`init`, `loaded`, `error_update`,
  `fetch_xhr_update`, `softnav`, `hidden`, `frozen`, `terminated`),
  not just on tab switch. Expect more than one `POST /c/` per visit.
- **`sendBeacon` doesn't show up under "Fetch/XHR" in DevTools.**
  Filter Network on `c/` (or use the "All" tab); sendBeacon
  requests appear under "Other".
