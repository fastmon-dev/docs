Eine **Site** ist eine Domain, die du überwachst. Sie gehört zu genau
einer [Application](/de/concepts/applications), die das Snippet und
die komplette Erfassungs-Config besitzt; die Site ist die reine
Analytics-Einheit — eigenes Dashboard, eigener Traffic, eigene
`site_id`.

Die meisten Applications haben eine Site. Weitere kommen dazu, wenn
sich mehrere Domains ein Snippet und eine Erfassungs-Config teilen
sollen; jede bleibt eine eigene Site mit eigenem Dashboard.

## Warum das wichtig ist

Die **Application** besitzt alles Beacon-Bezogene: das Script, das du
einbettest, die Hashes, das [Preset](/de/collection-modes), den
Collector. Eine **Site** ist der Ort, an dem die Daten einer Domain
landen, plus ein paar Per-Domain-Einstellungen, die du ohne Eingriff
in die Application anpassen kannst.

Willst du einen Dashboard-View über mehrere Domains, nimm **Tags**
(siehe unten) und aggregiere zur Query-Zeit. Ein Site-Group-Konzept
gibt es bewusst nicht; Tags reichen.

## Wann du sie anfasst

- **Domain hinzufügen.** Eine Site unter der Application anlegen (oder
  eine [vorgeschlagene Domain](/de/concepts/applications#unbekannte-domains-site_policy)
  adoptieren), dann das Snippet der Application einbetten.
- **Retention für eine Domain kürzen.** `data_retention_days` auf der
  Site überschreiben; sonst erbt sie den Default der Application.
- **Besucher-Identifier für eine Domain abschalten.** `store_stitch`
  auf der Site auf `off` überschreiben — echt anonyme Zeilen für diese
  Domain, auf Kosten ihrer Unique-Visitor-Zahlen.
- **Ohne Löschen pausieren.** `is_active = false` behält die Historie,
  stoppt neuen Ingest.
- **Cross-Domain-Reporting.** Tags wie `env:production` oder
  `team:growth`.

## Was eine Site hat

Eine Site ist bewusst schlank — Embed und Erfassungs-Config liegen auf
der [Application](/de/concepts/applications). Drei Felder sind
Per-Domain-**Overrides**: leer lassen, um den Default der Application
zu erben, oder setzen, um für diese Domain zu überschreiben.

| Feld                  | Typ                      | Hinweise                                                              |
| --------------------- | ------------------------ | --------------------------------------------------------------------- |
| `id`                  | UUID v7                  | Stabiler Identifier (= die ClickHouse-`site_id`).                    |
| `organization_id`     | UUID v7                  | Die besitzende Organisation.                                          |
| `application_id`      | UUID v7                  | Die Application, zu der diese Domain gehört.                          |
| `name`                | string                   | Wie die Site im UI erscheint.                                        |
| `domain`              | string                   | Reiner Hostname, kein Protokoll (z. B. `acme.com`).                  |
| `data_retention_days` | int · nullable           | Override; `null` erbt den Default der Application (`90`).            |
| `store_stitch`        | bool · nullable          | Override; `null` erbt den Default der Application.                   |
| `count_visitors_by`   | enum · nullable          | Override (`stitch` / `session`); `null` erbt den Default der Application. |
| `tags`                | Liste von Strings (max 10) | Freie Labels für Dashboard- und Analytics-Filter.                  |
| `is_active`           | bool                     | Bei `false` nimmt der Collector Beacons an, schreibt sie aber nicht in Analytics-Tabellen. |
| `activated_at`        | timestamp · nullable     | Wann die Site erstmals die Aktivierungsschwelle überschritt und live ging. |

Die Embed-Hashes, das Preset, der Collector, `site_policy` und das
Page-Type-Ruleset sind **nicht** hier — die liegen auf der
Application. Siehe [Applications](/de/concepts/applications).

## Tags

Tags sind kurze Labels, die du an eine Site vergibst. Dashboard und
Analytics-API filtern danach; so baust du „Production-Sites"- oder
„Marketing-Sites"-Views über mehrere Properties.

Konventionen, die gut funktionieren:

- `env:production`, `env:staging`, `env:preview`
- `team:growth`, `team:product`
- `region:eu`, `region:us`
- `tier:critical` für Sites, für die du enge Alarmschwellen setzt

Max 10 Tags pro Site.

## Welche Domains senden dürfen

Die früheren per-Site-Felder `allowed_origins` und
`enforce_domain_match` entfallen. Gesteuert wird der Ingest über die
[`site_policy`](/de/concepts/applications#unbekannte-domains-site_policy)
der Application: `strict` akzeptiert nur exakt registrierte
Domains, `open` (Default) schlägt unbekannte zur Adoption vor, und
`auto` provisioniert sie. Gesetzt wird das auf der Application.

## Per-Domain-Overrides

Zwei der erfassungsbezogenen Defaults der Application lassen sich pro
Site überschreiben, ohne zu ändern, was der Beacon sammelt:

- **`store_stitch`** — `off` verwirft den am Edge abgeleiteten `stitch`
  für diese Domain beim Insert und lässt echt anonyme Zeilen zurück,
  auf Kosten von Unique-Visitor- und Session-Metriken für diese Site.
  Per-Pageview-Signale (Web Vitals, Fehler, Third-Party, Attribution)
  bleiben unberührt.
- **`count_visitors_by`** — ob die **Visitors**-Metrik in den Reports
  dieser Site nach `stitch` oder `session` zählt. Eine
  Reporting-Präferenz, die zur Query-Zeit auf das begrenzt wird, was
  die Site tatsächlich speichert.

Lässt du eines von beiden leer, erbt die Site den Wert der
Application. Die
Begründung steht unter
[Privacy → Identifier ganz abschalten](/de/privacy#identifier-ganz-abschalten),
und die Erfassungs-Flags selbst unter [Presets](/de/collection-modes).

## Häufige Szenarien

### Production + Staging + Preview

Zwei Wege, beide funktionieren:

- **Eine Application, eine Site pro Domain** (`acme.com`,
  `staging.acme.com`, jeder Preview-Origin). Überall dasselbe Snippet;
  jede Domain bekommt ihr eigenes Dashboard und kann die Retention
  überschreiben. Nimm eine `dev`-[Environment](/de/concepts/applications#environment)-App,
  um Wegwerf-Traffic klar zu trennen.
- **Getrennte Applications**, wenn Staging wirklich andere
  Erfassungseinstellungen braucht (z. B. `full` auf Staging,
  `standard` in Prod).

Die meisten Teams starten mit einer Application und mehreren Sites.

### Auf eine neue Domain umziehen

Eine Site für die neue Domain unter derselben Application anlegen,
beide während des Cutovers laufen lassen, und die alte inaktiv
schalten, sobald der Traffic umgezogen ist.

## Häufige Überraschungen

- **Sites lassen sich nicht zwischen Organisationen umziehen.** Falls
  doch nötig: Support melden. (Eine Site zu einer anderen
  *Application* in derselben Org zu verschieben, geht — siehe
  [Applications](/de/concepts/applications#sites-adoptieren-verschieben-löschen).)
- **`is_active = false` behält die Historie.** Es stoppt nur neue
  Schreibvorgänge.
- **Das Snippet gehört zur Application, nicht zur Site.** Jede Site
  unter einer Application bettet denselben `source_hash` ein; ein
  Beacon wird anhand des Hostnamens der Seite einer Site zugeordnet.
- **Site löschen löscht auch die Beacon-Daten.** Mit Bestätigung.
  Kein Undo.
