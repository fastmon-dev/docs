Eine **Site** ist die Monitoring-Einheit in Fastmon. Praktisch
entspricht das einer Property: meistens einem Origin, einer App
oder einer Brand. Beacon-URL, Einstellungen, Dashboard-Filter: alles
pro Site.

## Warum das zählt

Was der Beacon tut, hängt komplett an der Site: das Script, der
[Collection Mode](/de/collection-modes), die Retention, die Allowed
Origins, die Daten im Dashboard. Neue Property monitoren = neue
Site anlegen.

Willst du einen Dashboard-View über mehrere Properties, nimm
**Tags** (siehe unten) und aggregier zur Query-Zeit. Ein
Site-Group-Konzept gibt es bewusst nicht; Tags reichen.

## Wann du sie anfasst

- **Neue Property hinzufügen.** Site anlegen, Snippet kopieren,
  einbetten.
- **Beacon-Erfassung anpassen.** Collection Mode der Site
  bearbeiten.
- **Staging oder Preview hinzufügen.** Staging-Origin in **Allowed
  Origins** eintragen, oder eine separate Site für Staging anlegen,
  wenn du isolierte Daten willst.
- **Retention reduzieren.** Default 90 Tage. Manche Sites wollen
  kürzer für Compliance, manche länger.
- **Ohne Löschen pausieren.** `is_active = false` behält Historie,
  stoppt neuen Ingest.
- **Cross-Site-Reporting taggen.** Tags wie `env:production` oder
  `team:growth`.

## Was eine Site hat

| Feld                  | Typ                                   | Hinweise                                                                          |
| --------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| `id`                  | UUID v7                               | Stabiler Identifier.                                                              |
| `organization_id`     | UUID v7                               | Die besitzende Organisation.                                                      |
| `name`                | string                                | Wie die Site im UI erscheint.                                                     |
| `domain`              | string                                | Reiner Hostname, kein Protokoll (z. B. `acme.com`).                               |
| `allowed_origins`     | komma-separierter String              | Origin-Allow-List für den Ingest. Leer = Origin-Check komplett aus.               |
| `collector_endpoint`  | string · nullable                     | Eigener Collector-Hostname für Enterprise-Routing. Default `fastmon.site`.        |
| `source_hash`         | string                                | Per-Site-Hash für die Script-URL (`/s/{source_hash}.js`).                         |
| `collector_hash`      | string                                | Per-Site-Hash für die Ingest-URL (`/c/{collector_hash}`).                         |
| `collection_mode`     | enum                                  | `anonymous`, `consent` oder `full`. Siehe [Collection Modes](/de/collection-modes). |

| `store_stitch`        | bool                                  | Default `true`. Bei `false` wird der am Edge abgeleitete `stitch` in jedem Modus verworfen — eine echt anonyme Zeile, auf Kosten von Visitor- und Session-Metriken. Siehe [Privacy](/de/privacy#identifier-ganz-abschalten). |
| `store_session`       | bool                                  | Default `true`. Bei `false` lässt das ausgelieferte Bundle `sessionStorage` aus und `sid` wird verworfen — volle Content-Telemetrie, keine seitenübergreifende Session-ID. |
| `enforce_domain_match`| bool                                  | Default `false`. Bei `true` werden Beacons verworfen, deren gemeldeter Seiten-URL-Host nicht `domain` oder eine Subdomain davon ist (siehe unten). |
| `source_version`      | string                                | Pinnt eine Beacon-Template-Version (`v1` aktuell).                                |
| `tags`                | Liste von Strings (max 10)            | Freie Labels für Dashboard- und Analytics-Filter.                                 |
| `is_active`           | bool                                  | Bei `false` nimmt der Collector Beacons noch an, schreibt sie aber nicht in Analytics-Tabellen. |

## Die zwei Hashes

Jede Site hat zwei Hashes. Sehen ähnlich aus, machen aber zwei
unterschiedliche Sachen.

- **`source_hash`** steht in der **Script-URL** und sagt, welche
  Beacon-Konfiguration an den Browser geliefert wird.
- **`collector_hash`** steht in der **Ingest-URL** und sagt, zu
  welcher Site eingehende Beacons gehören.

Getrennt sind sie, damit sich das Script-Template ändern kann (etwa
beim Beacon-Upgrade oder Collection-Mode-Wechsel), ohne dass die
Daten-Pipeline davon was mitkriegt. Du kopierst manuell nur den
`source_hash`; der `collector_hash` ist im Script drin und kommt
automatisch mit.

## Tags

Tags sind kurze Labels, die du an eine Site klebst. Dashboard und
Analytics-API filtern danach; so baust du „Production-Sites"- oder
„Marketing-Sites"-Views über mehrere Properties.

Konventionen, die gut funktionieren:

- `env:production`, `env:staging`, `env:preview`
- `team:growth`, `team:product`
- `region:eu`, `region:us`
- `tier:critical` für Sites, für die du aggressive Alarme einrichtest

Max 10 Tags pro Site.

## Allowed Origins

`allowed_origins` ist eine Opt-In-Allow-List. Sobald sie gesetzt
ist, akzeptiert der Collector nur Beacons, deren `Origin`-Header
einem Eintrag entspricht; die `domain` der Site ist dabei **nicht**
automatisch enthalten, also trag sie mit ein. Ist die Liste leer
(der Default), prüft der Collector den Origin gar nicht.

Beacons von nicht gelisteten Origins werden **still verworfen**:
Der Collector antwortet trotzdem mit `204`, damit im Browser nichts
bricht; es landen nur keine Daten. Fehlen Daten einer Domain auf
mysteriöse Weise, prüfe zuerst diese Liste.

Staging- und Preview-Hostnames hier eintragen. Wildcards nicht
unterstützt; jeden Origin explizit listen.

### Page-Domain erzwingen

`allowed_origins` prüft den HTTP-`Origin`-Header — aber
`sendBeacon` und Keepalive-POSTs lassen `Origin` oft weg, sodass
ein von einer fremden Seite mit bekanntem `collector_hash`
abgespielter Beacon an einer Origin-Allow-List vorbeirutschen kann.
`enforce_domain_match` (Opt-In, Default aus) schließt die Lücke von
der anderen Seite: aktiviert verwirft der Collector jeden Beacon,
dessen *gemeldeter Seiten-URL-Host* weder die `domain` der Site
noch eine Subdomain davon ist. Der Match ist label-gebunden
(`shop.example.com` matcht `example.com`, `notexample.com` nicht),
und ein Beacon mit leerem oder nicht parsbarem Host wird beim
Erzwingen verworfen.

Default aus, weil Multi-Domain- und Vanity-Domain-Setups sonst
legitimen Traffic verlieren. Für eine Single-Domain-Site, die den
Ingest auf die eigenen Seiten festnageln will, schalt es an.

## Privacy-Schalter

Zwei Schalter pro Site steuern, welche Identifier in den Storage
gelangen, ohne zu ändern, welche Datenkategorien der Beacon
sammelt:

- **`store_stitch`** (Default `true`). Aus verwirft den am Edge
  abgeleiteten `stitch`-Identifier beim Insert in *jedem* Collection
  Mode und lässt eine Zeile ganz ohne Besucher-Identifier zurück —
  vollständig anonym. Der
  Preis ist Analytics: keine Unique-Visitor-Zahlen und keine
  Session-Metriken (Bounce-Rate, Seiten pro Session, Verweildauer)
  für die Site. Per-Pageview-Signale (Web Vitals, Fehler,
  Third-Party, Attribution) bleiben unberührt.
- **`store_session`** (Default `true`). Aus sagt dem ausgelieferten
  Bundle, `sessionStorage` nie anzufassen, und der Collector
  verwirft `sid` als Absicherung. Eine `full`- oder `consent`-Site
  nach Opt-In behält dann die volle Content-Telemetrie (volle URLs,
  Fehler-Messages und -Frames), läuft aber ohne seitenübergreifende
  Session-ID. (`anonymous` hat ohnehin keine `sid`, also greift das
  nur unter `full` / `consent`.)

Die beiden sind unabhängig — schalte einen aus, beide oder keinen.
Die vollständige Begründung steht unter
[Privacy → Identifier ganz abschalten](/de/privacy#identifier-ganz-abschalten).

## Häufige Szenarien

### Production + Staging + Preview

Zwei Wege, beide tragen:

- **Eine Site, mehrere Origins** (`acme.com`, `staging.acme.com`
  und jeder Preview-Origin, der dich interessiert; keine
  Wildcards). Alle Daten in einem Topf, im Dashboard nach `domain`
  filtern. Billiger, dafür weniger sauber.
- **Drei Sites** mit eigener Retention und eigenen Tags. Saubere
  Daten, etwas mehr Setup.

Die meisten Teams landen nach ein paar Wochen bei der zweiten
Variante.

### Neue Sub-Site, gleiche Brand

Neue Site anlegen. Bloß nicht das Script-Tag einer anderen Property
wiederverwenden; der `source_hash` gehört zur Site, sonst sind
die Daten am Ende nicht mehr zuordenbar.

### Auf eine neue Domain umziehen

Neue Site für die neue Domain anlegen. Beide während des Cutovers
laufen lassen. Sobald kein Traffic mehr aufschlägt, die alte auf
inactive setzen.

## Häufige Überraschungen

- **Sites lassen sich nicht zwischen Organisationen umziehen.**
  Falls doch nötig: Support melden.
- **`is_active = false` behält die Historie.** Es stoppt nur neue
  Schreibvorgänge; gut für Pausen, nicht zum Retention-Kürzen.
- **Site umbenennen ändert die Hashes nicht.** Schon eingebettete
  Scripts laufen einfach weiter.
- **Site löschen löscht auch die Beacon-Daten.** Mit Bestätigung.
  Kein Undo.
