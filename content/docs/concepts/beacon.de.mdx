Der **Beacon** ist die JavaScript-Datei, die Fastmon unter
`https://fastmon.site/s/{source_hash}.js` ausliefert. Mehr
Client-Code haben wir nicht, und mehr laden deine Besucher auch
nicht von uns.

Diese Seite ist die technische Referenz. Fürs Setup geht's zur
[Implementierung](/de/install), für die Datenschutzposition zu
[Privacy: was wir nicht sammeln](/de/privacy).

## Drei Bundles, eine URL

Hinter demselben `<script>`-Tag liefert der Server pro Site einen
anderen Build aus, abhängig vom
[Collection Mode](/de/collection-modes):

| Mode | Bundle | Speicherfreier Default |
|---|---|:---:|
| `anonymous` | `anonymous.js` | Ja; keine Cookies, kein `sessionStorage` |
| `consent` | `consent.js` | Ja, bis `__fastmon_consent(true)`: danach `_fm_consent`-Cookie + `sessionStorage._s` |
| `full` | `full.js` | `sessionStorage._s` ab dem ersten Pageview, kein Cookie |

Du wählst das Bundle nicht im `<script>`-Tag; der Server löst es
aus dem Site-Mode auf und liefert den passenden Build aus. Ein
Mode-Wechsel rollt den Script-Cache automatisch.

## Warum das zählt

Der Beacon ist die Grenze zwischen Fastmon und deinem Besucher.
Was hier läuft (was gemessen wird, wann geflusht wird, welche
Identifier erzeugt werden) sieht der Browser, und es kann sich
jeder anschauen, der ins Script reinguckt. Daher halten wir die
Oberfläche klein: klein heißt auditierbar, schnell geladen und in
jedem Datenschutz-Review verteidigbar.

## Was der Beacon beobachtet

| Quelle                     | Was erfasst wird                                                               |
| -------------------------- | ------------------------------------------------------------------------------ |
| `PerformanceObserver`      | LCP, INP, CLS, FCP, Paint-Einträge, Long Animation Frames, Layout Shifts.      |
| `Navigation Timing`        | TTFB, Redirect-Count, Navigation-Typ (`navigate`, `reload`, `back_forward`).   |
| `Resource Timing`          | Pro Resource: Größe, Dauer, Kategorie. Pro Domain aggregiert.                  |
| `error`-Event              | Typ und Anzahl immer; Message + Frames nur mit Consent / `full`, und dort erst nach einem immer aktiven PII-Scrubber, der URLs, E-Mails, IDs und Strings in Anführungszeichen maskiert. |
| `unhandledrejection`       | Selbe Form wie `error`.                                                        |
| Page Visibility API        | Time-to-Hidden, gesamte sichtbare Zeit.                                        |
| Document & Window          | Seiten-URL (je nach Collection Mode bereinigt), Referrer, Viewport-Größenklasse. |

Geo-Daten (das Land) werden im Browser **nicht** gelesen. Der
Edge leitet sie aus der Request-IP ab und reicht einen Ländercode
als `FM-Country`-Header weiter; die IP selbst erreicht die
Anwendung nie. Genauso für die in Buckets eingeteilte Browser-/OS-/Geräte-
Familie, die als `FM-Browser` / `FM-Browser-Version` / `FM-OS` /
`FM-Device` weitergereicht wird. Zusätzlich berechnet der Edge
einen Einweg-`FM-Stitch`-Header
(`HMAC-SHA256(rotierendes-24h-Salt, IP | UA | collector_hash)` auf
128 Bit gekürzt), den das Backend für begrenzte
Cross-Pageview-Joins in allen Modi nutzt. Rechtlicher Rahmen unter
[Privacy → Der am Edge abgeleitete `stitch`-Identifier](/de/privacy#der-am-edge-abgeleitete-stitch-identifier).
Der Beacon selbst fragt nie nach Geolokation.

## Was der Beacon nicht tut

- `localStorage` / `IndexedDB` / `Cache Storage` lesen oder
  schreiben, in keinem Modus.
- Cookies in `anonymous` oder `full` setzen. In `consent` setzt er
  nach Opt-In genau eins (`_fm_consent`) und löscht es bei
  Opt-Out.
- URL-Query-Parameter oder Hash-Fragmente lesen.
- DOM-Inhalt anfassen (kein Scroll-Replay, kein Session-Replay,
  keine Formularerfassung).
- Mediengeräte, Sensoren oder Geolokation des Besuchers anfragen.
- Einen seitenübergreifenden Identifier in `anonymous` oder
  `consent` vor Opt-In minten. Die Per-Pageview-ID `pvid` gibt es
  in jedem Modus und stirbt mit dem Pageview.

## Lebenszyklus eines Pageviews

```
Seite lädt
  ├── Beacon-Script wird geladen (async, gecached, ETag-validiert)
  ├── Beacon registriert PerformanceObserver und Event-Listener
  ├── Besucher nutzt die Seite
  │     └── Beacon puffert Events im Speicher
  └── Flush-Trigger (visibilitychange→hidden, pagehide, Soft-Nav,
      Fehler-Update oder Terminate) lösen einen POST an
      /c/{collector_hash} aus, mit versioniertem Payload
      (Lifecycle markiert jede Emission)
```

Beim Flush versuchen wir zuerst `navigator.sendBeacon()`, damit der
Request auch beim Unload sicher rauskommt. Fehlt das, fallen wir auf
`fetch` mit `keepalive: true` zurück. Schlägt *beides* fehl (alte
Browser, sehr aggressives Extension-Blocking), greift ein
GET-Pixel-Fallback an `/c/{collector_hash}.gif?…`, der eine sichere
Teilmenge der Felder in den Query-String serialisiert. Sensible
Inhalte (`sid`, Referrer, Fehler, die großen Third-Party- /
Resource-Breakdown- / LoAF-JSON-Blobs) sind vom Pixel-Fallback
per Namen ausgeschlossen; sie wandern nie über eine
Access-Log-Oberfläche.

## Der Wire-Payload

Der Payload ist JSON mit absichtlich kurzen Keys, um den Body klein
zu halten. Der Body ist auf 8 KiB begrenzt. Alle Felder sind
optional; ein typischer Envelope sieht so aus:

```json
{
  "sid":  "01HZX...",
  "pvid": "01HZY...",
  "ver":  3,
  "lifecycle": "hidden",
  "pst":  1746604800000,
  "cst":  1746604803456,
  "u":    "https://acme.com/pricing",
  "r":    "https://google.com/",
  "b":    "Chrome",
  "v":    "120",
  "d":    "desktop",
  "o":    "macOS",
  "vc":   "wide",
  "c":    "4g",
  "t1":   320,
  "t2":   1100,
  "t9":   1820,
  "t10":  140,
  "t11":  0.05,
  "errs": [ { "t": "TypeError", "n": 1, "m": "...", "fr": "..." } ],
  "tv":   "260508-a1b2c3d",
  "dlv":  "b"
}
```

In der Praxis musst du das nicht lesen; Dashboard und
[Analytics-API](/en/api/analytics/queryAnalytics) packen das für dich aus.
Steht hier zum Nachschlagen.

Schlüssel-Abkürzungen:

- `sid`: Session-ID. Liegt im `sessionStorage._s`. Nur in `full`
  und in `consent` nach Opt-In.
- `pvid`: Per-Pageview-ID. Pro Pageview neu, nicht persistiert.
- `ver`: monoton steigende Version dieses Pageview-Payloads.
- `lifecycle`: einer von `init`, `loaded`, `error_update`,
  `softnav`, `hidden`, `frozen`, `terminated`.
- `pst`: Page-Started-Timestamp, Besucher-Wallclock (ms seit Epoch).
- `cst`: Client-Sent-At-Timestamp, Besucher-Wallclock zum Flush-Zeitpunkt.
  Server nutzt das, um Clock-Skew gegen die Empfangszeit zu erkennen.
- `u`, `r`: Seiten-URL und Referrer, beide vom Tracker auf
  Origin + Pathname vorbereinigt (Query und Hash entfernt). `r`
  wird serverseitig in gebucketete Source + Medium klassifiziert
  und der rohe Wert vor jedem Logging-Pfad verworfen. Er
  persistiert nie, in keinem Modus.
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`,
  `utm_content`, `click_id_param`: Kampagnen-Attribution aus
  `window.location.search`. Jeweils auf 64 Zeichen begrenzt.
  `click_id_param` ist nur das Plattform-*Label* (`"gclid"` /
  `"fbclid"` / …); der Click-ID-Wert wird vom Tracker verworfen.
  In jedem Modus auf der Leitung.
- `b`, `v`, `d`, `o`, `vc`, `c`: Browser-Familie, Browser-Major,
  Device-Klasse, OS-Familie, Viewport-Klasse, Connection-Typ. Die
  ersten vier kommen aus `FM-*`-Edge-Headern; `vc` und `c` aus dem
  Browser. `rtt` / `dl` gesellen sich als Echtzeit-RTT- und
  Downlink-Schätzungen dazu.
- `pre`, `ad`, `vd`: Prerender-Flag (Speculation Rules API),
  Activation-Delta (ms, nur bei prerendered Pages) und
  Visibility-Dirty (war der Tab während des Pageviews im
  Hintergrund).
- `t1`…`t36`: numerische Timing-Slots (TTFB, FCP, LCP, INP, CLS,
  Cache-Hit-Rate, Resource-Breakdowns, LoAF-Aggregate, …).
- `errs`: Error-Einträge (`t` Typ, `n` Count, `m` Message, `fr`
  Frames). `m` und `fr` sind consent-only; auch dann laufen sie
  durch einen Scrubber, der URLs, E-Mails, IDs und Strings in
  Anführungszeichen maskiert.
- `tv`: Tracker-Version, Format `YYMMDD-<git-sha>[-dirty]`.
- `dlv`: Delivery-Methode (`b` für `sendBeacon`, leer für `fetch`).

## Cache und Rollouts

Das Script wird mit starkem Cache und `ETag` ausgeliefert. Zwei
Dinge invalidieren den Cache automatisch:

- **Collection-Mode-Wechsel.** Schaltest du eine Site von
  `anonymous` auf `consent` (oder umgekehrt), liefert das eine neue
  Template-Version aus.
- **Beacon-Upgrade.** Fastmon liefert Beacon-Versionen
  (`source_version`); ein Wechsel der gepinnten Version rollt den
  Cache.

Du musst dafür nicht redeployen. Beim nächsten Cache-Check holt
der Browser sich die neue Version automatisch.

## Kunden-JS-API

Zwei Integrationspunkte, beide namensstabil über Bundle-Versionen:

### Sample-Rate (alle Bundles)

```js
// 10 % der Pageviews werden getrackt (Default 1.0 = 100 %)
window.__FASTMON_SAMPLE_RATE = 0.1;
```

Wird beim Tracker-Reset einmal pro Pageview gelesen. Die
Entscheidung gilt pro Pageview, nicht pro Beacon: ein gesampelter
Pageview emittiert alle seine Lifecycle-Beacons, ein ungesampelter
keinen. Erlaubter Bereich `[0, 1]`; Werte außerhalb werden
ohne Hinweis begrenzt. Setz das vor dem Script-Tag, wenn auch der
allererste Beacon respektiert werden soll.

### Consent-Toggle (nur `consent`-Bundle)

```js
window.__fastmon_consent(true);   // Besucher hat Opt-In gegeben
window.__fastmon_consent(false);  // Besucher hat abgelehnt / widerrufen
```

`true` setzt das `_fm_consent`-Cookie und schaltet die volle
Wire-Form frei; `false` löscht das Cookie *und* räumt die
Session-ID im Speicher ab. Idempotent. Den Wire-Effekt findest du
unter [Collection Modes](/de/collection-modes).

## Collection Modes

Die Runtime des Beacons hängt am
[Collection Mode](/de/collection-modes) der Site:

- `anonymous`: beobachtet und sendet ohne expliziten
  Besucher-Identifier (kein `sid`, keine LCP-Image-URL, keine
  LoAF-Script-Pfade, keine Third-Party-Domain-Map, bei Fehlern
  nur Typ + Count). Der am Edge abgeleitete `stitch`-Header liegt
  in allen Modi vor; siehe
  [Privacy](/de/privacy#der-am-edge-abgeleitete-stitch-identifier).
- `consent`: auf dem Wire byte-identisch zu `anonymous`, bis der
  CMP des Kunden `window.__fastmon_consent(true)` aufruft. Nach
  Opt-In byte-identisch zu `full`. Intern liest der Tracker das
  `_fm_consent`-Cookie und signalisiert dem Collector den
  aufgelösten Modus per `?p=1`-Query-Parameter (das Cookie ist die
  Wahrheit; der Query-Parameter ist nur der Hinweis für die
  serverseitige Auflösung).
- `full`: behält alle erfassten Felder.

In jedem Mode gelten die Datenschutz-Garantien aus
[Privacy](/de/privacy).

## Rate-Limiting

Der Collector rate-limitet pro `(collector_hash, Client-IP)`. Die
IP wird am Edge nur für diesen Bucket gelesen; die Anwendung
bekommt einen vorbereiteten Bucket-Key zu sehen, nicht die rohe IP,
und die IP landet nicht auf der Platte. Das ist eine Schutzmaßnahme:
eine kaputte Seite oder ein synthetischer Lasttest soll den Ingest
für andere Tenants nicht zumüllen. Mit echtem Traffic läufst du da
praktisch nie rein.

Wird ein Beacon rate-limitet, kommt eine `429` zurück. Der Browser
wirft den Buffer weg und macht weiter; sonst passiert nichts.

Payloads über 8 KiB werden mit `413` abgelehnt. Liegt `cst` mehr
als 5 Minuten neben der Server-Uhr, fällt der Server auf seine
eigene Empfangszeit zurück, statt abzulehnen; der Beacon wird
trotzdem akzeptiert.

## Was du wissen solltest

- **SPA-Route-Wechsel starten einen neuen Pageview.** Das Script
  bleibt geladen, aber Soft-Navs (gepatchtes `history.pushState`
  und `popstate`) generieren einen neuen `pvid`, setzen die
  Web-Vitals-Observer zurück und flushen einen `softnav`-Beacon
  für den vorherigen Pageview. Ein Tab kann also viele Pageviews
  emittieren.
- **Mehrere Flushes pro Pageview.** Geflusht wird bei den Lifecycle-
  Triggern `init`, `loaded`, `error_update`, `softnav`, `hidden`,
  `frozen`, `terminated`: nicht nur beim Tab-Wechsel. Pro Besuch
  siehst du in der Regel mehrere `POST /c/`.
- **`sendBeacon` taucht in DevTools nicht unter „Fetch/XHR" auf.**
  Network-Tab nach `c/` filtern (oder „All" benutzen); sendBeacon-
  Requests landen unter „Other".
