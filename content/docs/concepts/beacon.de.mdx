Der **Beacon** ist die JavaScript-Datei, die Fastmon unter
`https://fastmon.site/s/{source_hash}.js` ausliefert. Mehr
Client-Code haben wir nicht — und mehr laden deine Besucher auch
nicht von uns.

Diese Seite ist die technische Referenz. Fürs Setup geht's zur
[Implementierung](/de/install), für die Datenschutzposition zu
[Privacy: was wir nicht sammeln](/de/privacy).

## Warum das zählt

Der Beacon ist die Grenze zwischen Fastmon und deinem Besucher.
Was hier läuft — was gemessen wird, wann geflusht wird, welche
Identifier erzeugt werden — sieht der Browser, und es kann sich
jeder anschauen, der ins Script reinguckt. Deshalb halten wir die
Oberfläche klein: klein heißt auditierbar, schnell geladen und in
jedem Datenschutz-Review verteidigbar.

## Was der Beacon beobachtet

| Quelle                     | Was erfasst wird                                                               |
| -------------------------- | ------------------------------------------------------------------------------ |
| `PerformanceObserver`      | LCP, INP, CLS, FCP, Paint-Einträge, Long Animation Frames, Layout Shifts.      |
| `Navigation Timing`        | TTFB, Redirect-Count, Navigation-Typ (`navigate`, `reload`, `back_forward`).   |
| `Resource Timing`          | Pro Resource: Größe, Dauer, Kategorie. Aggregiert zu Per-Domain-Rollups.       |
| `error`-Event              | Typ, Message, Stack-Frames (fingerprinted, nicht wörtlich gespeichert).        |
| `unhandledrejection`       | Selbe Form wie `error`.                                                        |
| Page Visibility API        | Time-to-Hidden, gesamte sichtbare Zeit.                                        |
| Document & Window          | Seiten-URL (je nach Collection Mode bereinigt), Referrer, Viewport-Größenklasse. |

Geo-Daten (Land, Region) werden im Browser **nicht** gelesen — der
Collector leitet sie serverseitig aus der Request-IP ab und verwirft
sie. Der Beacon fragt nie nach Geolokation.

## Was der Beacon nicht tut

- Cookies setzen.
- `localStorage` / `IndexedDB` / `Cache Storage` lesen oder schreiben.
- URL-Query-Parameter oder Hash-Fragmente lesen.
- DOM-Inhalt anfassen (kein Scroll-Replay, kein Session-Replay, keine
  Formularerfassung).
- Mediengeräte, Sensoren oder Geolokation des Besuchers anfragen.
- Persistenten Identifier minten — die Per-Pageview-ID wird nicht
  persistiert.

## Lebenszyklus eines Pageviews

```
Seite lädt
  ├── Beacon-Script wird geladen (async, gecached, ETag-validiert)
  ├── Beacon registriert PerformanceObserver und Event-Listener
  ├── Besucher nutzt die Seite
  │     └── Beacon puffert Events im Speicher
  └── Flush-Trigger (visibilitychange→hidden, pagehide, Soft-Nav,
      Fehler-Update oder Terminate) lösen einen POST an
      /c/{collector_hash} aus, mit versioniertem Payload
      (Lifecycle markiert jede Emission)
```

Beim Flush versuchen wir zuerst `navigator.sendBeacon()`, damit der
Request auch beim Unload sicher rauskommt. Fehlt das, fallen wir auf
`fetch` mit `keepalive: true` zurück.

## Der Wire-Payload

Der Payload ist JSON mit absichtlich kurzen Keys, um den Body klein
zu halten. Der Body ist auf 4 KiB begrenzt. Alle Felder sind
optional; ein typischer Envelope sieht so aus:

```json
{
  "sid":  "01HZX...",
  "pvid": "01HZY...",
  "ver":  3,
  "lifecycle": "hidden",
  "pst":  1746604800000,
  "cst":  1746604803456,
  "u":    "https://acme.com/pricing",
  "r":    "https://google.com/",
  "b":    "Chrome",
  "v":    "120",
  "d":    "desktop",
  "o":    "macOS",
  "vc":   "wide",
  "c":    "4g",
  "t1":   320,
  "t2":   1100,
  "t9":   1820,
  "t10":  140,
  "t11":  0.05,
  "errs": [ { "t": "TypeError", "n": 1, "m": "...", "fr": "..." } ],
  "tv":   "260508-a1b2c3d",
  "dlv":  "b"
}
```

In der Praxis musst du das nicht lesen — Dashboard und
[Analytics-API](/de/analytics-api) packen das für dich aus.
Steht hier zum Nachschlagen.

Schlüssel-Abkürzungen:

- `sid` — Session-ID. Wird in `anonymous` weggelassen.
- `pvid` — Per-Pageview-ID.
- `ver` — monoton steigende Version dieses Pageview-Payloads.
- `lifecycle` — einer von `init`, `loaded`, `error_update`,
  `softnav`, `hidden`, `frozen`, `terminated`.
- `pst` — Page-Started-Timestamp, Besucher-Wallclock (ms seit Epoch).
- `cst` — Client-Sent-At-Timestamp, Besucher-Wallclock zum Flush-Zeitpunkt.
  Server nutzt das, um Clock-Skew gegen die Empfangszeit zu erkennen.
- `u`, `r` — Seiten-URL und Referrer (Referrer in `anonymous` weg).
- `b`, `v`, `d`, `o`, `vc`, `c` — Browser-Familie, Browser-Major,
  Device-Klasse, OS-Familie, Viewport-Klasse, Connection-Typ.
- `t1`…`t36` — numerische Timing-Slots (TTFB, FCP, LCP, INP, CLS, …).
- `errs` — Error-Einträge (`t` Typ, `n` Count, `m` Message, `fr` Frames).
- `tv` — Tracker-Version, Format `YYMMDD-<git-sha>[-dirty]`.
- `dlv` — Delivery-Methode (`b` für `sendBeacon`, leer für `fetch`).

## Cache und Rollouts

Das Script wird mit starkem Cache und `ETag` ausgeliefert. Zwei
Dinge invalidieren den Cache automatisch:

- **Collection-Mode-Wechsel.** Schaltest du eine Site von
  `anonymous` auf `consent` (oder umgekehrt), liefert das eine neue
  Template-Version aus.
- **Beacon-Upgrade.** Fastmon liefert Beacon-Versionen
  (`source_version`); ein Wechsel der gepinnten Version rollt den
  Cache.

Du musst dafür nicht redeployen. Beim nächsten Cache-Check holt
der Browser sich die neue Version automatisch.

## Collection Modes

Die Runtime des Beacons hängt am
[Collection Mode](/de/collection-modes) der Site:

- `anonymous` — beobachtet und sendet ohne Identifier (kein `sid`,
  kein Referrer, keine LCP-Image-URL, keine LoAF-Details, keine
  Third-Party-Domain-Map).
- `consent` — schaltet pro Request zwischen anonym und full um, per
  `?p=`-Query-Parameter auf der Collector-URL (`p=1` für full,
  fehlend oder `0` für anonymous).
- `full` — behält alle erfassten Felder.

In jedem Mode gelten die Datenschutz-Garantien aus
[Privacy](/de/privacy).

## Rate-Limiting

Der Collector rate-limited im Speicher pro
`(collector_hash, Client-IP)`. Die IP dient nur diesem Bucket und
landet nie auf der Platte. Das ist defensiv gemeint: eine kaputte
Seite oder ein synthetischer Lasttest soll den Ingest für andere
Tenants nicht zumüllen. Mit echtem Traffic läufst du da praktisch
nie rein.

Wird ein Beacon rate-limited, kommt eine `429` zurück. Der Browser
wirft den Buffer weg und macht weiter — sonst passiert nichts.

Payloads über 4 KiB werden mit `413` abgelehnt. Liegt `cst` mehr
als 5 Minuten neben der Server-Uhr, fällt der Server auf seine
eigene Empfangszeit zurück, statt zu rejecten — der Beacon wird
trotzdem akzeptiert.

## Was du wissen solltest

- **SPA-Route-Wechsel starten einen neuen Pageview.** Das Script
  bleibt geladen, aber Soft-Navs (gepatchtes `history.pushState`
  und `popstate`) generieren einen neuen `pvid`, setzen die
  Web-Vitals-Observer zurück und flushen einen `softnav`-Beacon
  für den vorherigen Pageview. Ein Tab kann also viele Pageviews
  emittieren.
- **Mehrere Flushes pro Pageview.** Geflusht wird bei den Lifecycle-
  Triggern `init`, `loaded`, `error_update`, `softnav`, `hidden`,
  `frozen`, `terminated` — nicht nur beim Tab-Wechsel. Pro Besuch
  siehst du in der Regel mehrere `POST /c/`.
- **`sendBeacon` taucht in DevTools nicht unter "Fetch/XHR" auf.**
  Network-Tab nach `c/` filtern (oder "All" benutzen) — sendBeacon-
  Requests landen unter "Other".
