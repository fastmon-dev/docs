A **site** is the unit of monitoring in fastmon. In practice that maps to a property: usually one origin, one app, or one brand. Beacon URL, settings, dashboard filters: all per site.

## Why it matters

Everything beacon-related lives on the site: the script you embed, the [tracker settings](/en/tracker), retention, allowed origins, the data in the dashboard. New property to monitor = new site.

To organize related properties, attach **tags** (below). A cross-site analytics scope that reports on every site carrying a tag together is planned; today tags are labels for grouping, not an analytics filter.

## When you'd touch it

- **Adding a new property.** Create a site, copy the snippet, embed.
- **Changing what the beacon collects.** Edit the site's [tracker settings](/en/tracker), or pick a [preset](/en/tracker).
- **Adding a staging or preview environment.** Add the staging origin to **allowed origins**, or create a separate site for staging if you want isolated data.
- **Cutting retention.** Default is 90 days. Some sites want shorter for compliance, some want longer.
- **Pausing without deleting.** Toggle `is_active = false` to keep history but stop ingesting new data.
- **Tagging to organize sites.** Add tags like `env:production` or `team:growth`.

Sites created in the dashboard start on the **Standard** preset, which sets `store_stitch`, `track_query_keys`, `error_frame_detail`, and `fetch_xhr_enabled` on.

## The two hashes

Each site has two hashes. They look similar but do two different jobs.

- **`source_hash`** sits in the **script URL** and tells us which site's beacon config to ship to the browser.
- **`collector_hash`** sits in the **ingest URL** and tells us which site an incoming beacon belongs to.

They're separate so the script template can change (for a beacon upgrade or a settings change) without affecting the data pipeline. You only ever copy `source_hash` by hand; `collector_hash` is baked into the script and rides along.

## Tags

Tags are short labels you attach to a site to group related properties (a "production sites" or "marketing sites" grouping). The sidebar's per-site tag filter was removed; a proper cross-site analytics scope that reports on every site carrying a tag together is planned. For now, tags are labels and don't filter analytics.

Conventions that work well:

- `env:production`, `env:staging`, `env:preview`
- `team:growth`, `team:product`
- `region:eu`, `region:us`
- `tier:critical` for sites you alert on aggressively

Max 10 tags per site.

## Allowed origins

`allowed_origins` is an opt-in allow-list. When it's set, the collector only accepts beacons whose `Origin` header matches one of its entries; the site's `domain` is **not** implicitly included, so list it too. When the list is empty (the default), the collector doesn't check the origin at all.

A beacon from a non-listed origin is **silently dropped**: the collector still answers `204` so nothing breaks in the browser, but no data lands. If a domain's data is mysteriously missing, this list is the first thing to check.

Add staging and preview hostnames here. Wildcards aren't supported; list each origin explicitly.

### Enforcing the page domain

`allowed_origins` checks the HTTP `Origin` header — but `sendBeacon` and keepalive POSTs frequently omit `Origin`, so a beacon replayed from a foreign page that knows your `collector_hash` can slip past an origin allow-list. `enforce_domain_match` (opt-in, default off) closes that gap from the other side: when enabled, the collector drops any beacon whose *reported page-URL host* is neither the site's `domain` nor a subdomain of it. The match is label-bounded (`shop.example.com` matches `example.com`; `notexample.com` does not), and a beacon with an empty or unparseable host is dropped while enforcing.

It's off by default because multi-domain and vanity-domain deployments would lose legitimate traffic. Turn it on for a single-domain site that wants ingest locked to its own pages.

## Privacy levers

Two per-site switches control whether any visitor identifier reaches storage, without changing what categories of data the beacon collects. Under the default `Standard` preset `store_stitch` is **on** and `store_session` is **off**; the `Minimal` preset turns both off:

- **`store_stitch`** (default `false`). On stores the edge-derived `stitch` identifier for unique-visitor counts and session metrics (bounce rate, pages per session, dwell time). Off leaves a row with no visitor identifier at all, fully anonymous. Per-pageview signals (Web Vitals, errors, third-party, attribution) are unaffected either way.
- **`store_session`** (default `false`). On serves the stateful bundle, which writes a `sessionStorage` session id for cross-page linkage; whether that write waits for consent is [`preconsent_level`](/en/tracker#preconsent-level). Off tells the served bundle to never touch `sessionStorage`, and the collector drops `sid` as a backstop.

The two are independent, enable either, both, or neither. See [Tracker settings](/en/tracker) for every switch and [Privacy → Turning identifiers off, or leaving them off](/en/privacy#turning-identifiers-off-or-leaving-them-off) for the reasoning.

## Common scenarios

### Production + staging + preview

Two shapes that work:

- **One site, several origins** (`acme.com`, `staging.acme.com`, and each preview origin you care about; no wildcards). All data lands in one bucket; filter by `domain` in the dashboard. Cheaper, less clean.
- **Three sites** with their own retention and tags. Cleaner data, more setup.

Most teams end up on the second one after a few weeks.

### A new sub-site, same brand

New site. Don't reuse the script tag from another property; the `source_hash` is per site, and the data has to be attributable.

### Moving to a new domain

Create a new site for the new domain, run both during the cutover, and mark the old one inactive once traffic's moved over.

## Common surprises

- **Sites can't move between organizations.** Ping support if you really need it.
- **`is_active = false` keeps the history.** It just stops new writes. Use it for pauses, not for cutting retention.
- **Renaming a site doesn't change its hashes.** Already-embedded scripts keep working.
- **Deleting a site deletes its beacon data.** With a confirmation step. No undo.
