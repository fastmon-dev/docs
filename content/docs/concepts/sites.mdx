A **site** is one domain you monitor. It belongs to exactly one
[application](/en/concepts/applications), which owns the snippet and
all collection config; the site is the pure analytics unit — its own
dashboard, its own traffic, its own `site_id`.

Most applications have one site. Add more when several domains should
share one snippet and one collection config; each stays a separate
site with its own dashboard.

## Why it matters

The **application** owns everything beacon-related: the script you
embed, the hashes, the [preset](/en/collection-modes), the collector.
A **site** is where the data for one domain lands, plus a few
per-domain settings you can tune without touching the application.

For one dashboard view across several domains, use **tags** (below)
and aggregate at query time. There's no site-group concept on
purpose; tags cover it.

## When you'd touch it

- **Adding a domain.** Create a site under the application (or adopt a
  [suggested domain](/en/concepts/applications#unknown-domains-site_policy)),
  then embed the application's snippet.
- **Cutting retention for one domain.** Override `data_retention_days`
  on the site; otherwise it inherits the application's default.
- **Dropping the visitor identifier for one domain.** Override
  `store_stitch` off on the site — genuinely anonymous rows for that
  domain, at the cost of its unique-visitor counts.
- **Pausing without deleting.** Toggle `is_active = false` to keep
  history but stop ingesting new data.
- **Cross-domain reporting.** Add tags like `env:production` or
  `team:growth`.

## What's on a site

A site is deliberately slim — the embed and collection config live on
the [application](/en/concepts/applications). Three fields are
per-domain **overrides**: leave them empty to inherit the
application's default, or set them to override for this domain.

| Field                 | Type                     | Notes                                                                 |
| --------------------- | ------------------------ | --------------------------------------------------------------------- |
| `id`                  | UUID v7                  | Stable identifier (= the ClickHouse `site_id`).                       |
| `organization_id`     | UUID v7                  | The owning organization.                                              |
| `application_id`      | UUID v7                  | The application this domain belongs to.                               |
| `name`                | string                   | How the site appears in the UI.                                       |
| `domain`              | string                   | Bare hostname, no protocol (e.g. `acme.com`).                         |
| `data_retention_days` | int · nullable           | Override; `null` inherits the application's default (`90`).           |
| `store_stitch`        | bool · nullable          | Override; `null` inherits the application's default.                  |
| `count_visitors_by`   | enum · nullable          | Override (`stitch` / `session`); `null` inherits the application's default. |
| `tags`                | list of strings (max 10) | Free-form labels for dashboard and analytics filtering.               |
| `is_active`           | bool                     | When false, beacons are accepted but not written to analytics tables. |
| `activated_at`        | timestamp · nullable     | When the site first crossed the activation threshold and went live.   |

The embed hashes, preset, collector, `site_policy`, and page-type
ruleset are **not** here — they're on the application. See
[Applications](/en/concepts/applications).

## Tags

Tags are short labels you attach to a site. The dashboard and
analytics API let you filter by tag, so they're how you build a
"production sites" or "marketing sites" view across multiple
properties.

Conventions that work well:

- `env:production`, `env:staging`, `env:preview`
- `team:growth`, `team:product`
- `region:eu`, `region:us`
- `tier:critical` for sites you alert on aggressively

Max 10 tags per site.

## Restricting which domains send data

The old per-site `allowed_origins` and `enforce_domain_match` are
gone. Ingest is now governed by the application's
[`site_policy`](/en/concepts/applications#unknown-domains-site_policy):
`strict` accepts only exactly-registered domains, `open` (default)
suggests unknown ones for adoption, and `auto` provisions them. Set it
on the application.

## Per-domain overrides

Two of the application's collection-related defaults can be overridden
per site, without changing what the beacon collects:

- **`store_stitch`** — off drops the edge-derived `stitch` for this
  domain at insert time, leaving genuinely anonymous rows, at the cost
  of unique-visitor and session metrics for that site. Per-pageview
  signals (Web Vitals, errors, third-party, attribution) are
  unaffected.
- **`count_visitors_by`** — whether the **visitors** metric counts by
  `stitch` or `session` in this site's reports. A reporting
  preference, clamped at query time to what the site actually stores.

Leave either unset to inherit the application. See
[Privacy → Turning identifiers off entirely](/en/privacy#turning-identifiers-off-entirely)
for the reasoning, and [Presets](/en/collection-modes) for the
collection flags themselves.

## Common scenarios

### Production + staging + preview

Two shapes that work:

- **One application, one site per domain** (`acme.com`,
  `staging.acme.com`, each preview origin). Same snippet everywhere;
  each domain gets its own dashboard and can override retention. Use a
  `dev` [environment](/en/concepts/applications#environment) app to
  keep throwaway traffic clearly separate.
- **Separate applications** when staging genuinely needs different
  collection settings (e.g. `full` on staging, `standard` in prod).

Most teams start with one application and several sites.

### Moving to a new domain

Add a site for the new domain under the same application, run both
during the cutover, and mark the old one inactive once traffic's
moved over.

## Common surprises

- **Sites can't move between organizations.** Ping support if you
  really need it. (Moving a site to another *application* in the same
  org is fine — see [Applications](/en/concepts/applications#sites-adopt-move-delete).)
- **`is_active = false` keeps the history.** It just stops new writes.
- **The snippet is per application, not per site.** Every site under
  an application embeds the same `source_hash`; a beacon is matched to
  a site by the page's hostname.
- **Deleting a site deletes its beacon data.** With a confirmation. No
  undo.
