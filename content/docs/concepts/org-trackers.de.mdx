Eine [Site](/de/concepts/sites) ist eine Property mit eigenem Beacon. Ein **org-weiter Tracker** ist ein Beacon, das du über **mehrere Domains mit gemeinsamer Code-Basis** einbindest, sodass du ein einziges Snippet pflegst statt eins pro Domain. Der klassische Fall: Länder-Shops auf `shop.de`, `shop.fr`, `shop.it`, gebaut aus demselben Frontend.

Der `collector_hash` des Trackers löst beim Ingest anhand des Hostnames der Seite die richtige Site auf, sodass jede Domain weiterhin auf ihrer **eigenen Site** landet, mit eigener Auswertung und Konfiguration. Du hast ein Embed und trotzdem getrennte Auswertung pro Domain.

## Wann du ihn nutzt

- **Mehrere Domains, eine Code-Basis.** Länder- oder Marken-Shops, oder ein Multi-Region-Deployment, wo ein eigenes Snippet pro Domain ein Pflege-Aufwand wäre.
- **Du willst trotzdem Analytics pro Domain.** Jede registrierte Domain wird getrennt ausgewertet; der org-weite Tracker ist nur der Auslieferungsweg.

Nimm einen normalen [Site](/de/concepts/sites)-Tracker, wenn eine Property für sich steht, oder wenn du **unterschiedliches Erfassungsverhalten pro Domain** brauchst (siehe unten).

## Wie das Routing funktioniert

Jedes Beacon trägt die Seiten-URL. Beim Ingest liest der Collector den **Hostname** aus dieser URL und gleicht ihn gegen die Sites deiner Organisation ab:

- **Exakter Hostname-Match.** `Site.domain` muss gleich dem beobachteten Hostname sein. `shop.de` matcht die Site `shop.de`; `www.shop.de` oder `de.shop.com` matchen **nicht** eine als `shop.de` registrierte Site. Registriere jede Domain, die du auslieferst, als eigene Site.
- **Match:** Das Beacon landet auf dieser Site, gestempelt mit ihrer `site_id`, genau wie bei einem Per-Site-Tracker.
- **Kein Match:** Der Hostname wird für die [Discovery](#discovery-unbekannte-hostnames) festgehalten und das Beacon nicht geschrieben.

Das Setup ist also: einen org-weiten Tracker anlegen, jede Domain als Site registrieren, das Snippet des Trackers überall einbinden.

## Einstellungen gelten org-weit

Ein org-weiter Tracker liefert **ein Bundle** an jede Domain, also gelten seine Daten- und Routing-[Tracker-Einstellungen](/de/tracker) (`store_session`, `preconsent_level`, `store_error_messages`, `error_frame_detail`, `track_query_keys`, `query_value_keys`, `fetch_xhr_enabled`, `collector_mode`, `collector_endpoint`) **für jede Domain gleich**. Er nimmt dieselben [Presets](/de/tracker#presets).

Drei Einstellungen bleiben **pro Site**, aufgelöst auf der gematchten Site beim Ingest:

- [`store_stitch`](/de/tracker#store-stitch), beim Schreiben der Zeile pro Site erzwungen,
- [`preferred_identity`](/de/tracker#preferred-identity), eine Reporting-Vorgabe pro Site,
- [`enforce_domain_match`](/de/tracker#enforce-domain-match) und [`allowed_origins`](/de/concepts/sites#allowed-origins), die Ingest-Schutzmechanismen, die auf der aufgelösten Site greifen.

Wenn du wirklich unterschiedliches Erfassungsverhalten pro Domain brauchst (etwa Session-Tracking auf einem Shop, auf einem anderen nicht), ist das das Signal, dieser Domain einen eigenen Per-Site-Tracker zu geben.

## Besucher über Domains hinweg

Der am Edge abgeleitete [`stitch`](/de/tracker#store-stitch) enthält die Seiten-**Domain** im Input, also bekommt derselbe Besucher auf `shop.de` und auf `shop.fr` je einen **anderen** `stitch`. Ein org-weiter Tracker zählt die Besucher jeder Domain getrennt; er führt einen Besucher nicht domainübergreifend zusammen. Er ist eine Auslieferungs- und Routing-Erleichterung (ein Embed, eine Site pro Domain), keine domainübergreifende Identität. Alles andere am `stitch` (begrenzte ≤24 h Verknüpfbarkeit, Forward Secrecy, nichts auf dem Gerät gespeichert) bleibt gleich; siehe [Privacy → der am Edge abgeleitete `stitch`](/de/privacy#der-am-edge-abgeleitete-stitch-identifier).

## Discovery: unbekannte Hostnames

Meldet der Tracker einen Hostname, der zu keiner registrierten Site passt, verwirft fastmon ihn nicht still: er **zählt ihn und bietet ihn als Vorschlag an**, sodass du die fehlende Domain als Site hinzufügen kannst. Das fängt einen neuen Länder-Shop oder eine vergessene Staging-Domain, die das Snippet schon trägt. Vorschläge leben etwa eine Woche und sind pro Organisation gedeckelt; verwirf die, die du nicht willst. Bis ein Hostname als Site registriert ist, werden seine Beacons nicht geschrieben.

## Was auf einem org-weiten Tracker steht

| Feld | Hinweise |
| --- | --- |
| `id` | UUID v7. |
| `organization_id` | Die besitzende Organisation. Eine Org kann mehrere Tracker haben. |
| `name` | Label, im Dashboard angezeigt. |
| `source_hash` | Per-Tracker-Hash in der Script-URL (`/s/{source_hash}.js`). |
| `collector_hash` | Per-Tracker-Hash in der Ingest-URL (`/c/{collector_hash}`), zugleich der Edge-Stitch-Anker. |
| Daten- + Routing-Einstellungen | `store_session`, `preconsent_level`, `store_error_messages`, `error_frame_detail`, `track_query_keys`, `query_value_keys`, `fetch_xhr_enabled`, `collector_mode`, `collector_endpoint`. Ins ausgelieferte Bundle gebacken, org-weit. Siehe [Tracker-Einstellungen](/de/tracker). |
| `source_version` | Pinnt die Beacon-Template-Version. |
| `is_active` | Aus werden Beacons angenommen, aber nicht geschrieben. |

`store_stitch`, `preferred_identity` und `enforce_domain_match` stehen **nicht** auf dem Tracker; sie liegen auf der jeweils aufgelösten Site.

## `domain` vs. `hostname`

Zwei verwandte Begriffe, bewusst getrennt:

- **`domain`** ist der Wert, den du auf einer Site konfigurierst (`Site.domain`, in der API, im Dashboard, in Reports). Er ändert sich nicht.
- **`hostname`** ist der beobachtete Wert: der aus der Seiten-URL geparste Host beim Ingest. Org-Tracker-Routing und Discovery matchen auf dem Hostname.
