Network Error Logging (NEL) meldet die Requests, die im Browser deiner Besucher scheitern: DNS-Fehler, abgelehnte Verbindungen, Timeouts, TLS-Fehler und 4xx- oder 5xx-Antworten.

<Callout type="info" title="Nur Chromium">
  Reports schicken Chrome, Edge, Opera, Samsung Internet und andere Chromium-Browser. Safari und Firefox schicken keine, jede Zahl ist also eine Untergrenze.
</Callout>

## Einrichten [#setup]

Zwei Response-Header auf deinem Origin schalten die Reports ein. Header, Server-Beispiele, Prüfung und Fallen stehen im Guide [Network Error Logging einrichten](/de/guides/network-error-logging).

## Die Seite Network Error Logging [#dashboard]

Die Seite liegt in der Sidebar unter **Fehler → Network Error Logging**, unter `/errors/nel`. Sie hat drei Tabs, der Tab steht in der URL.

- **Übersicht**: die HTTP-Fehler des Servers, 5xx oben, 4xx darunter. **Betroffene Besucher** steht bei jeder Zahl vorn, mit dem Anteil an allen Besuchern, die Reports danach. Das Diagramm stapelt **Nach Klasse** oder **Nach Code**.
- **Wo sie scheitern**: eine Karte pro Dimension, alle auf einmal. Statuscodes, Seiten, Serveradressen, Länder, Seiten und Hosts, Geräte, Browser, OS, Traffic und Versionen, sobald ein Browser gefiltert ist.
- **Seiten und Hosts** ist zugleich der Setup-Check. Jede Site zeigt ihren letzten Report, und zeigen die meisten Reports ohne Details auf eine Serveradresse, nennt die Karte sie als wahrscheinlich ausgefallen.
- **Verbindungsfehler**: standardmäßig zugeklappt. Jeder Typ wird mit seinem üblichen Niveau verglichen, markiert werden ein kaputtes Zertifikat und ein Anstieg bei abgelehnten Verbindungen, Timeouts oder unbekannten Hosts.
- **Pfade**: erst die Hosts, darin jeweils ihre Pfade.
- **Reports**: jeder NEL-Report, der neueste zuerst, aufklappbar mit allen gespeicherten Feldern. Mehrere Reports eines Typs von einem Besucher auf einer Seite hintereinander stehen als eine Zeile da. Jeder Report hat einen eigenen Link zum Teilen, und speichert die Site eine Besucher-ID, verlinkt er auf die Journey des Besuchers.

**Filtern** geht wie auf den anderen Seiten: `+` neben einem Wert filtert darauf, `-` schließt ihn aus, und die Lupe öffnet die Reports der Zeile. Die Kacheln 5xx und 4xx filtern eine ganze Statusklasse. Die Filter der Seite (Status, Fehlertyp, Host, Pfad, Seite, Serveradresse) stehen im Filter-Panel unter **Nur auf dieser Seite** und bleiben in der URL. **Abgebrochene Ladevorgänge** sind ausgeblendet, auf der Seite und in der Journey eines Besuchers, jeweils mit einem Schalter zum Einblenden.

Die Journey eines Besuchers unter [Visitors](/de/analytics#visitors) zeigt seine NEL-Reports zwischen den Seitenaufrufen, in zeitlicher Reihenfolge und jeweils als solche markiert.

## Klassen [#classes]

Jeder Report hat eine Klasse, `nel_class`, abgeleitet aus seinem Typ. In Klammern steht das Label im Dashboard.

| Klasse | Typen | Bedeutung |
| --- | --- | --- |
| `http_error` (Serverfehler (4xx/5xx)) | `http.error` | Dein Server hat mit 4xx oder 5xx geantwortet. |
| `connection` (Verbindung) | `dns.*`, `tcp.*`, `tls.*`, `h2.*`, `h3.*`, `http.response.*`, `unknown` | Keine brauchbare Antwort. |
| `abandoned` (Abgebrochen) | `abandoned` | Der Request wurde abgebrochen, meist weil der Besucher weg ist, während er noch lud. |
| `downgraded` (Vom Browser verdeckt) | `dns.address_changed` | Der Browser hat den echten Typ verborgen. Siehe [mehrere Adressen](#several-addresses). |
| `other` (Sonstige) | alles andere | Ein Typ, den bisher kein Browser geschickt hat. |

## Fehlertypen [#error-types]

Die Typen, die dir am häufigsten begegnen. In den Details jedes Reports steht der Typ des Browsers, im Dashboard ein lesbarer Name.

| Typ | Was passiert ist | Wiederholt der Browser |
| --- | --- | --- |
| `http.error` | Der Server hat mit 4xx oder 5xx geantwortet. | nur 408 auf einer wiederverwendeten HTTP/1.1-Verbindung und 421 |
| `dns.name_not_resolved` | Das DNS kennt keine Adresse für den Host. | nein |
| `dns.failed`, `dns.timed_out` | Die Namensauflösung ist fehlgeschlagen oder hat zu lange gedauert. | nein |
| `dns.address_changed` | Ein Fehler, dessen Typ der Browser verborgen hat. | wie der verborgene Typ |
| `tcp.refused` | Der Server hat die Verbindung abgelehnt. | nein |
| `tcp.timed_out` | Verbindung oder Request hat zu lange gedauert. | nein |
| `tcp.reset`, `tcp.closed`, `tcp.aborted` | Die Verbindung ist abgerissen. | auf einer wiederverwendeten Verbindung |
| `tls.cert.*` | Das Zertifikat ist ungültig, abgelaufen, nicht vertrauenswürdig, widerrufen oder für einen anderen Host. | nein |
| `tls.version_or_cipher_mismatch` | Browser und Server haben keine gemeinsame TLS-Version oder Cipher. | nein |
| `h2.ping_failed` | Die HTTP/2-Verbindung antwortet nicht mehr. | bis zu zweimal |
| `http.response.*` | Die Antwort war nicht lesbar, etwa leer oder abgeschnitten. | teils, auf einer wiederverwendeten Verbindung |
| `abandoned` | Der Request wurde vor dem Ende abgebrochen. | nein |
| `unknown` | Ein Browserfehler ohne eigenen Namen, die Ursache ist verloren. | teils |

## Einen Report lesen [#reading]

- **`http.error`** ist der einzige Typ, der sagt, dass dein Server mit einem Fehler geantwortet hat. Er gilt für jeden Request an den Origin, auch für Bilder und API-Calls.
- **`tls.cert.*`, `tls.version_or_cipher_mismatch` und `http.response.*`** deuten ebenfalls auf deine Seite.
- **`abandoned`, `tcp.reset`, `tcp.closed`, `tcp.aborted`, `h2.ping_failed` und `unknown`** sind ein Grundrauschen, das jede Site hat. Besucher gehen, während noch etwas lädt, und Mobilfunknetze verlieren Verbindungen.
- **Ein plötzlicher Anstieg von `tcp.refused` oder `tcp.timed_out`** heißt, dass der Server keine Verbindungen mehr annimmt oder beantwortet.
- **Ein Report beweist nicht, dass ein Besucher den Fehler gesehen hat.** Bei manchen Typen meldet der Browser zuerst und schickt den Request dann erneut, oft mit Erfolg. Ein Fehler kann außerdem mehrere Reports hinterlassen.

## Sites hinter mehreren Adressen [#several-addresses]

Zwei Ingress-Knoten, ein CDN oder IPv4 neben IPv6 legen mehrere Adressen hinter einen Namen. Der Browser speichert die Policy zusammen mit der Adresse, von der sie kam. Fällt eine Adresse aus, schickt nur noch die andere die Policy, und die Fehler der toten Adresse kommen als `dns.address_changed` ohne Status und Dauer an.

- **Steigt die Klasse `downgraded`** auf so einer Site, fällt eine Adresse aus.
- **`server_ip`** nennt die Adresse, an die ein Request ging. Die Karte **Serveradressen** oder eine Aufschlüsselung der `downgraded`-Reports nach `server_ip` zeigt die ausgefallene.
- **Eine Fehlerseite ohne Header** von der anderen Adresse geht verloren, der Ingress muss sie also auf jede Antwort setzen. Prüf das an einem 404, wie unter [Prüfen](/de/guides/network-error-logging#verify).

Gespeichert wird nur eine öffentliche `server_ip`. Siehe [Datenschutz → NEL-Reports](/de/privacy#nel-reports).

## Grenzen [#limits]

- **Nur Chromium-Browser.** Jede Zahl ist eine Untergrenze.
- **Besucherzahlen brauchen [`store_stitch`](/de/tracker#store-stitch).** Eine Site ohne zählt bei den Reports mit, nicht aber bei **Betroffene Besucher**, und die Seite nennt sie.
- **Eine kleinere `failure_fraction`** macht die Besucherzahl zur Untergrenze.
- **Ein Netzwechsel trennt den Besucher.** Ein Report bekommt seine Besucher-ID beim Upload, ein Report aus einem neuen Netz passt also nie zu den Seitenaufrufen davor.
- **Die ID rotiert täglich.** Ein Report, der nach der Rotation hochgeladen wird, kann bei einem neuen Besucher landen.

## API [#api]

Alle drei Routen nehmen dieselben `filters`, darunter `error_type`, `nel_class`, `status_code_range`, `server_ip`, `host`, `path` und `page_url` samt `exclude`. Jede andere Analytics-Route lehnt diese Filter mit 422 ab.

| Route | Liefert |
| --- | --- |
| [`POST /analytics/nel`](/de/api/analytics/queryAnalyticsNel) | Anzahl, Zeitreihe, Fehlertypen, Statuscodes, Zeit bis zum Fehler und die Top-Pfade pro Host |
| [`POST /analytics/nel/breakdown`](/de/api/analytics/queryAnalyticsNelBreakdown) | Reports nach einer `dimension` gruppiert, mit Anteil und Besuchern |
| [`POST /analytics/nel/reports`](/de/api/analytics/listAnalyticsNelReports) | Einzelne Reports, der neueste zuerst, seitenweise per `cursor`. `filters.report_id` wählt einen aus. |

Die Zählungen sind mit `1 / failure_fraction` gewichtet, einzelne Reports nicht. Ohne `error_type`-Filter zählt jeder Typ mit, auch `abandoned`. [Visitor-Detail](/de/api/analytics/getAnalyticsVisitorDetail) und [Checkout-Journeys](/de/api/analytics/queryAnalyticsCheckoutJourneys) liefern `nel_reports` neben `pages` und `events`: fehlt das Feld, wurde nicht nachgesehen, `[]` heißt keine Reports.
