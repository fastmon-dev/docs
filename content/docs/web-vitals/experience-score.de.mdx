**Experience Score** ist eine Composite-Metrik. Sie verdichtet LCP,
INP und CLS zu einer einzigen 0–100-Zahl pro Pageview. Praktisch
ist das die Zahl fürs Dashboard, fürs Status-Reporting und für den
Moment, in dem du Performance jemandem erklärst, der kein
Engineering-Hintergrund hat.

Mathematik und Schwellen kommen von Google, die Gewichtung folgt
dem
[PageSpeed-Insights-Modell](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring).
Wir rechnen den Score aus deinen Real-User-Daten.

## Was ist ein guter Score?

| Score           | Rating              |
| --------------- | ------------------- |
| 90–100          | **Gut**             |
| 50–89           | Verbesserungswürdig |
| 0–49            | Schlecht            |

90 heißt: alle drei Core Web Vitals stehen für den Großteil deines
Traffics auf "gut". Ein Score in den 50ern heißt fast immer: zwei
Metriken sind okay, eine (meistens INP) hängt im roten Bereich.

## Wie der Score berechnet wird

Jeder Core Web Vital wird über eine Log-Normal-Kurve, kalibriert
gegen Googles "gut"-/"verbesserungswürdig"-Schwellen, auf einen
0–100-Sub-Score abgebildet:

| Metrik | Gut (volle Punktzahl) | Schlecht (null Punkte) |
| ------ | --------------------- | ---------------------- |
| LCP    | ≤ 2.500 ms            | ≥ 4.000 ms             |
| INP    | ≤ 200 ms              | ≥ 500 ms               |
| CLS    | ≤ 0,1                 | ≥ 0,25                 |

Die drei Sub-Scores werden gewichtet:

| Metrik | Gewicht |
| ------ | ------- |
| LCP    | 35 %    |
| INP    | 35 %    |
| CLS    | 30 %    |

Die gewichtete Summe ist der Experience Score. Pageviews ohne Wert
für eine Metrik (z. B. INP, wenn der Besucher nie interagiert hat)
nutzen die vorhandenen Sub-Scores, anteilig neu gewichtet.

## Wann der Score berechnet wird

Pro Pageview, beim Verstecken der Seite — derselbe Trigger, der die
zugrundeliegenden Metriken finalisiert. Die Aggregat-Scores im
Dashboard sind Durchschnitte über den gewählten Zeitraum.

## Experience Score in Fastmon ansehen

Die Headline-Zahl steht auf dem **Performance**-Dashboard.
Darunter siehst du den Breakdown — welcher Sub-Score den Total nach
unten zieht — und einen Trend-Chart über das gewählte Fenster.

Nützliche Slices:

- **Nach URL** — Group by URL. Welche Seiten dominieren den
  Durchschnitt?
- **Nach Release** — `compare_to_release_id`. Das beste einzelne
  Signal für "hat dieser Deploy UX verschlechtert?"
- **Nach Land / Device** — Group by `country` oder `device_type`.
  Regionale oder Device-Klassen-Regressionen sind im globalen Score
  meist unsichtbar.

## Wie man einen niedrigen Score verbessert

Der Composite ist nur so gesund wie sein schwächster Bestandteil:

1. Den Breakdown öffnen und den **schlechtesten Sub-Score**
   identifizieren.
2. Die zugehörige Metrik-Seite lesen ([LCP](/de/web-vitals/lcp),
   [INP](/de/web-vitals/inp), [CLS](/de/web-vitals/cls)) und den
   Fix mit der höchsten Leverage anwenden.
3. Nach dem Release nachprüfen. `compare_to_release_id` für ein
   sauberes Vorher/Nachher.

Nicht versuchen, alle drei gleichzeitig zu optimieren. Die
Verbesserungen schlagen sich oft gegenseitig — LCP-Fix mit mehr JS
kann INP verschlechtern, Platz für Ads gegen CLS kann LCP nach
hinten schieben.

## Häufige Überraschungen

- **Der Score kann fallen, ohne dass eine einzelne Metrik eine
  Schwelle reißt.** Eine kleine Regression in zwei Metriken kann
  den Composite um 5–10 Punkte bewegen, während jede Metrik
  einzeln noch "Gut" sagt.
- **Ein einzelner Deploy kann eine permanente Score-Lücke
  erzeugen.** Sobald eine Regression live ist, trägt jeder folgende
  Pageview die schlechtere Zahl in den Durchschnitt. Den Tag des
  Deploys zu erwischen, zählt.
- **Seiten mit wenigen Interaktionen haben aufgeblasene Scores.**
  Wenn Besucher nie interagieren, fällt INP weg — der Score
  reflektiert dann nur LCP und CLS, was meist leichter ist.
- **Interner vs. externer Traffic verzerrt den Composite.**
  Office-Traffic auf warmen Caches und schnellen Laptops scort
  super; echte Besucher auf Mobile in einem Tunnel scoren
  schlechter. Interne IPs ausfiltern, damit die Zahl ehrlich
  bleibt.
