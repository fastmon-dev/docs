title: Presets
description: Minimal, standard, full — the collection presets, what each collects, and which one to pick.
---

Every Fastmon application has a **collection preset**. It decides what
the tracker collects in the visitor's browser and how much is retained.
One setting on the application; switch it any time and the served script
updates automatically — no redeploy, no tag change.

Three presets: `minimal`, `standard`, `full`. The default is `standard`,
and for almost everyone that's the right pick. A preset is just a
shortcut: it expands into a handful of individual settings (see
[Fine-tuning](#fine-tuning-the-individual-settings)), so you can start
from a preset and change one flag — the app then labels the result
`custom`.

## Compare at a glance

|                                   | `minimal`                       | `standard` (default)                     | `full`                          |
| --------------------------------- | ------------------------------- | ---------------------------------------- | ------------------------------- |
| Web Vitals                        | Yes                             | Yes                                      | Yes                             |
| Unique visitors                   | No                              | Yes (edge-derived `stitch`)              | Yes                             |
| Multi-page sessions               | No                              | No                                       | Yes                             |
| Storage on the visitor's device   | None                            | None                                     | `sessionStorage` session id     |
| Page-URL query params             | Stripped                        | Key names kept, values dropped           | Key names kept, values dropped  |
| Errors                            | Type + count, frame hosts only  | + full stack frames (host, path, line/col) | + the error message           |
| fetch / XHR endpoint timing       | No                              | Yes                                      | Yes                             |
| Consent gate for the session id   | —                               | —                                        | None by default (written on load) |
| When to pick                      | Leanest possible; no visitor identifier at all | Almost everyone       | Session analytics, or internal apps |

Every preset shares the same privacy floor: no cookies, no IP storage,
no raw User-Agent, no fingerprinting. See [Privacy](/en/privacy).

## `standard`: the default

Standard is what a new application starts on, and it's the right pick
for almost every public website.

You get Web Vitals, error diagnostics with full stack frames (but not
the free-form error message), fetch/XHR endpoint timing, and
**unique-visitor counts** — all without writing anything to the
visitor's device.

Unique visitors come from the **`stitch`**: a pseudonymous id the
Fastmon edge derives from the request (IP and User-Agent), never from
the client. The salt rotates about daily and lives only in edge memory,
so joinability is bounded to ≤24h with forward secrecy, and nothing is
stored in the browser. See
[the edge-derived `stitch`](/en/privacy#the-edge-derived-stitch-identifier).

What standard does **not** do:

- write to the visitor's device (no cookies, no `localStorage` /
  `sessionStorage`),
- carry a cross-page session id (that's `full`),
- keep error **message** text (only the type, count, and stack frames),
- keep query-parameter **values** (it keeps the key names; values are
  dropped unless a key is on the allow-list).

**Pick standard if:** you run a public site and want real diagnostics
and visitor counts with the simplest posture — no cookies and no device
storage for our beacon.

## `minimal`: the leanest

Minimal turns every optional setting off. You get core Web Vitals and
error type + count (frame hosts only, no paths, no message) — and
nothing that identifies a visitor.

Because it drops the `stitch` too, **minimal has no unique-visitor
metric at all**: those counts read as unmeasurable (blank), not zero.
Query strings are stripped entirely (`/p?a=1#x` → `/p`), there's no
fetch/XHR timing, and no device storage.

**Pick minimal if:** you want the absolute leanest footprint and don't
need visitor counts or per-endpoint timing — the strictest posture, or a
site where even a bounded pseudonymous id is more than you want.

## `full`: sessions and message-level detail

Full keeps everything standard collects and adds:

- a **cross-page session id** so pageviews link into a session
  (journeys, funnels, return-visitor metrics). It's the one thing
  written to the device — `sessionStorage["_fms"]`, which dies with the
  tab. Enabled by `collect_sessions`.
- the **error message** (still run through the PII scrubber before it
  leaves the browser), on top of the stack frames standard already
  keeps.

Full ships with the session id written **on page load** — there's no
consent gate by default (`session_consent` is `immediate`). If you
need to withhold the session id until a consent manager allows it, see
[Gating the session id behind consent](#gating-the-session-id-behind-consent).

**Pick full if:** you want session-level analytics, or you're
internal-only (intranet, employee app) where the visitor and consent
context are different, or you have a legal basis that covers a
cross-page identifier.

If you're unsure, stay on standard. A cross-page session id is a bigger
privacy step; don't take it unless you need what it gives you.

## Gating the session id behind consent

None of the three presets waits for consent — standard stores no session
id at all, and full writes it on load. If you store sessions **and** must
hold the session id until your consent manager (CMP) allows it, that's a
**custom** configuration: keep `collect_sessions` on but set
`session_consent` to `deferred`.

With that combination the served script defers the one device write
(`sessionStorage["_fms"]`) until your CMP calls:

```js
// In your cookie banner's "accept" handler:
window.fastmon.grantConsent();
```

`grantConsent()` is write-only and idempotent; call it once consent is
granted. There is no revoke call — before consent nothing was written,
so there's nothing to clear.

Two things worth being precise about:

- This gates **only the on-device session-id write**, not collection.
  Beacons still fire before consent — Web Vitals, errors, the
  unique-visitor `stitch` — just with an empty session id. Consent
  unlocks cross-page **linkage**, not new categories of data.
- Without `collect_sessions` there's nothing to gate: the bundle never
  touches storage, so consent doesn't apply.

(An older `window.__fastmon_consent()` call still exists as a deprecated
alias, but prefer `grantConsent()`.)

## Fine-tuning: the individual settings

A preset just sets the flags below; you can also set them one by one, in
which case the app labels the result `custom`.

- **`collect_sessions`** (full only) — the `sessionStorage` session id for
  multi-page sessions. The only setting that writes to the device.
- **`store_stitch`** (standard, full) — keep the edge-derived visitor
  `stitch`. Off makes the stored row genuinely anonymous, at the cost of
  unique-visitor counts. No device storage either way.
- **`session_consent`** — `deferred` defers the session-id write until
  `grantConsent()`; `immediate` writes it on load. Only matters when
  `collect_sessions` is on.
- **`collect_query_keys`** (standard, full) — keep query-parameter key
  names (values still dropped, except allow-listed keys). Off strips the
  whole query string.
- **`collect_error_frames`** (standard, full) — keep full stack frames
  (host, path, line/col). Off collapses frames to their host only.
- **`collect_error_messages`** (full only) — keep the free-form error
  message (PII-scrubbed). Separate from frame detail.
- **`collect_fetch_xhr`** (standard, full) — collect fetch/XHR endpoint
  timing and errors.

See [Privacy → Turning identifiers off entirely](/en/privacy#turning-identifiers-off-entirely)
for the reasoning behind the identifier switches.

## Changing the preset

In Fastmon, open the application, go to its collection settings, and pick
a different preset (or tune the individual settings). The change takes
effect when the script cache rolls over — usually within minutes for
active visitors, immediately for new ones. You don't redeploy or change
the `<script>` tag.
