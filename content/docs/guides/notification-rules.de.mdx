---
title: Notification Rules
description: Alarm, wenn eine Metrik eine Schwelle reißt oder gegen ein Release regrediert.
---

Eine **Notification Rule** prüft im Takt eine Bedingung und feuert
eine Notification, wenn die Bedingung zutrifft. Zwei Muster decken
ab, was die meisten Teams brauchen:

- **Schwellenüberschreitung** — "Alarm, wenn LCP bei p75 über 3.000
  ms steigt."
- **Release-Regression** — "Alarm, wenn eine Metrik nach dem
  Release deutlich schlechter ist als davor."

Dieser Guide zeigt beide. Die Engine dahinter ist dieselbe — nur
die Bedingung sieht anders aus.

**Setup-Zeit:** etwa zehn Minuten pro Rule.
**Was du brauchst:** Org-Mitgliedschaft mit Recht zum Anlegen von
Rules (jede Rolle reicht für eigene Rules).

## Wo Rules leben

Rules sind Organisations-Ressourcen. Jede Rule gehört dem User, der
sie erstellt hat, aber andere Org-Mitglieder können sie sehen.
Notifications gehen ans Delivery-Target der Rule — Default ist die
E-Mail des Erstellers.

## 1. Preset wählen (oder leer starten)

In Fastmon **Notifications → Rules → New rule** öffnen. Der erste
Schritt zeigt **Presets** — übliche Rule-Formen mit sinnvollen
Defaults:

- *LCP-Regression auf Production*
- *Error-Spike auf einer URL*
- *INP wurde poor*
- *Experience Score gefallen*
- … und ein paar weitere.

Den nehmen, der am nächsten dran ist. Felder lassen sich danach
beliebig anpassen. Passt nichts: **Blank rule** und weiter zu
Schritt 3.

## 2. Delivery-Target wählen

Vier Target-Typen sind unterstützt:

- **E-Mail** — eine oder mehrere Adressen.
- **Slack** — native Incoming-Webhook-Integration.
- **Discord** — native Incoming-Webhook-Integration.
- **Webhook** — POST an eine URL mit JSON-Payload. Damit deckst du
  Teams, Mattermost, PagerDuty, Opsgenie oder jedes andere Tool mit
  Incoming-Webhook-URL ab.

Mehrere Targets pro Rule möglich. Jedes feuert auf dasselbe Event.

## 3. Bedingung definieren

Der Teil mit dem meisten Hirnschmalz. Eine Rule besteht aus drei
Bausteinen:

### Was du misst

- Eine **Site** (oder "all sites" für eine Portfolio-Rule).
- Eine **Metrik** (LCP, INP, CLS, FCP, TTFB, Fehlerrate, Sessions, …).
- Eine **Aggregation** (p50, p75, p95, count, avg, …).
- Optional **Filter** (nur Mobile, ein bestimmter URL-Pattern, eine
  Länderliste, …).

### Wann du misst

- Ein **Zeitfenster** — meist 1 h oder 24 h. Kürzere Fenster fangen
  schneller, sind aber lauter.
- Eine **Evaluation-Cadence** — wie oft die Rule läuft (alle 15 min,
  stündlich, täglich).

### Was eine Verletzung ist

Wähle eines von:

- **Über/unter Schwelle** — fixe Zahl. "LCP p75 > 3.000 ms."
- **Regrediert vs. Vorfenster** — relativ zum gleich langen
  Vorgänger-Fenster. "LCP p75 +20%."
- **Regrediert vs. Release** — relativ zum gleich langen Fenster,
  das beim `released_at` eines Release endet. "LCP p75 +20% vs.
  Release `01HZX...`." (Nützlich, um in CI Deploys scheitern zu
  lassen.)

Jede Variante hat ihre eigene Stolperfalle:

- **Absolute Schwellen sind stabil** — bestrafen dich aber an dem
  Tag, an dem dir ein neues, großes Segment auf die Site kommt
  (mehr Slow-Network-Besucher → schlechtere Metrik → Alarm, gegen
  den du nichts machen kannst).
- **Relative Schwellen sind empfindlich**, dafür auf
  Low-Volume-Sites laut. Ein schlechter Day-over-Day-Vergleich
  reicht zum Feuern. Da hilft der `min_volume`-Guard.
- **Per-Release-Schwellen sind präzise**, feuern aber nur, wenn du
  Releases auch wirklich getaggt hast. Siehe
  [Releases vergleichen](/de/guides/compare-releases).

## 4. Rule trocken testen

Bevor du speicherst, **Evaluate now** klicken. Damit läuft die
Rule einmal gegen das **aktuelle** Fenster — und sagt dir, ob sie
feuern würde. Guter Sanity-Check für deine Schwelle: feuert sie
bei jedem Test, ist die Schwelle zu eng.

API-Pendant: `POST /notification-rules/{id}/evaluate`.

## 5. Synthetischen Test schicken

Nach dem Speichern **Send test notification** klicken. Schickt eine
Beispiel-Nachricht an alle Delivery-Targets, damit du bestätigen
kannst, dass sie ankommen.

API-Pendant: `POST /notification-rules/{id}/test`.

## 6. History beobachten

Jede Rule hat einen **History**-Tab, der jede Auswertung listet, ob
sie gefeuert hat und (wenn ja) wohin die Notification ging. Wenn
ein Alarm mal nicht zu dem passt, was du im Dashboard siehst, ist
die History der Audit-Trail.

## Worked Example: LCP-Regression auf Production

Ziel: Alarm, wenn LCP bei p75 auf der Production-Site mehr als 20%
schlechter ist als die vorherigen 24 Stunden.

| Feld             | Wert                                      |
| ---------------- | ----------------------------------------- |
| Site             | `acme-marketing` (Production)             |
| Metrik           | `lcp`                                     |
| Aggregation      | `p75`                                     |
| Filter           | `tags: [env:production]`                  |
| Zeitfenster      | letzte 24 Stunden                         |
| Cadence          | stündlich                                 |
| Bedingung        | Regrediert vs. Vorfenster (+20 %)         |
| Min Volume       | 500 Pageviews im Fenster                  |
| Delivery         | `team-perf@example.com`                   |

Der Min-Volume-Guard ist das, was am häufigsten vergessen wird —
ohne ihn feuern dir nächtliche Low-Volume-Phasen pausenlos
False-Positives.

## Häufige Überraschungen

- **Rules dedupen nicht zwischen Cadences.** Eine 15-Minuten-Rule
  feuert bei anhaltender Regression locker 4× in der Stunde. Wer
  nur eine Notification pro Vorfall will: längere Cadence oder
  `min_silence_minutes` auf der Rule.
- **Auch in einem geplanten Wartungsfenster ist ein Alarm Lärm.**
  Rule pausieren — oder per URL die betroffenen Pfade ausschließen.
- **Notification Rules taggen Releases nicht von selbst.** Für
  Per-Release-Alarme musst du
  [Releases vergleichen](/de/guides/compare-releases) erst mal
  verdrahten.
