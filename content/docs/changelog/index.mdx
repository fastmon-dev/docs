The latest from fastmon, across the dashboard, API, platform, and tracker. You can filter the feed by area.

We cover the changes you should know about, not every internal tweak. The exception is the **tracker** (the script you embed on your site): we document it in full, because it runs in your visitors' browsers, where even a small change can affect what your pages measure.

<Changelog>

<ChangelogEntry date="2026-09-24" type="new" area="api" title="An application can store a share of its visitors">

`collection.sampling_rate` on the application sets the share of visitors whose beacons are stored, `1.0` by default.

- **The edge decides once per visitor**, so a visitor's pageviews are kept or dropped together. A new rate applies within about a minute.
- **Traffic counts are scaled back up** on every analytics endpoint, in Ask, in MCP and in the weekly mail. Percentiles, shares and minimum-sample thresholds stay on the stored rows.
- **Stored rows** still drive the Beacon explorer, the funnel stage counts and the histograms.
- **The lowest rate is `0.1`.** The API refuses anything below it. Only an application that stores `stitch` is sampled, and checkout events never are.
- **`meta.sampling`** on every analytics response names the lowest rate configured in scope and whether it is below `1.0`.

Docs: [Applications → Traffic sampling](/en/concepts/applications#sampling).

</ChangelogEntry>

<ChangelogEntry date="2026-09-24" type="removed" area="tracker" title="The tracker ignores `__FASTMON_SAMPLE_RATE`">

The tracker no longer reads `window.__FASTMON_SAMPLE_RATE`, so a page that still sets it sends every pageview. Sampling is the application setting `collection.sampling_rate` now, decided per visitor at the edge. Docs: [Applications → Traffic sampling](/en/concepts/applications#sampling).

</ChangelogEntry>

<ChangelogEntry date="2026-09-23" type="new" area="dashboard" title="Geographic distribution as a globe">

The section draws the world as a globe or a flat map, beside the country list.

- **The globe opens on your traffic.** A shop selling into one market lands on that market. Drag turns it, the wheel zooms, and the arrow keys, plus and minus work too.
- **The flat map keeps the poles in proportion**, so Greenland no longer looks like a continent. Zoom and reset buttons sit on the map.
- **The chosen view stays in the URL**, so a reload or a shared link opens the same one.
- **Clicking a country shows its filter buttons.** The highlight follows the pointer and no longer sticks after you leave.
- The section has a heading on the dashboard.

</ChangelogEntry>

<ChangelogEntry date="2026-09-21" type="fixed" area="platform" title="Shopify checkout events join the storefront visitor">

A Shopify pixel's checkout events now carry the same visitor identifier as the shop's pageviews. The funnel no longer counts a buyer twice, and the visitor's journey shows the checkout. Events collected before the change stay detached.

At the switch every visitor identifier changed once, as it does at the daily salt rotation. An application serving several domains now counts a visitor once across all of them. Docs: [Privacy → stitch](/en/privacy#the-edge-derived-stitch-identifier).

</ChangelogEntry>

<ChangelogEntry date="2026-09-20" type="new" area="dashboard" title="A visitor's journey shows the Shopify checkout">

Checkout started, payment submitted and order placed now sit between the pageviews, in the order they happened. An event from before the selected window shows with a negative offset. Grouped by session, the journey says why its checkout half is missing.

</ChangelogEntry>

The list applied an "at least 3 pages" filter nobody had set, so one- and two-page visitors were missing. All filters now start empty, and the page-count filter still works when you set it.

</ChangelogEntry>

<ChangelogEntry date="2026-09-20" type="changed" area="api" title="Every API field follows one vocabulary">

One name, one type and one scale per concept, across responses, request bodies and query parameters alike.

- **Time is `timestamp`.** Every series point, event and journey row answers it, in place of `at`, `t`, `bucket` and `ts`.
- **Shares are fractions, 0 to 1.** `share`, `with_error_share`, `relative_change` and `progress` replace `percentage`, `percentage_of_total`, `share_pct`, `change_percent` and `percent`.
- **First party versus third party is one field**, `ownership`, with the values `first_party`, `third_party` and `mixed`. It replaces `bucket`, `is_first_party` and `by_bucket`.
- **Durations and counts carry their unit and their noun**: `duration_ms`, `p75_ms`, `time_to_success_seconds`, `error_count`, `frame_count`, `sample_count`.
- **Closed vocabularies are enums**, among them the funnel `stage`, `granularity`, `device_type` and `identity`. A generated client gets a type rather than a free string.
- **No response field is nullable.** 444 declared `T | null` for a value the API never sends, because a field with no value is left out. Nothing on the wire changes, and a generated client now sees an optional field.
- **Each deprecated name points at its successor** through `x-replaced-by` in the OpenAPI document, so a migration can be driven from the spec.

Docs: [API → Analytics](/en/api/analytics/queryAnalytics).

</ChangelogEntry>

<ChangelogEntry date="2026-09-20" type="changed" area="api" title="An analytics response separates result, request and paging">

A response used to mix the answer, the paging and an echo of the request in one flat object.

- **`meta` carries the facts about the answer**: `execution_time_ms`, and for a list `total`, `limit`, `offset` and `has_more` in one place.
- **`request` carries what the server actually used**: the window with a relative range already resolved to its two ends, the bucket width, the identity and the filters.
- **Every list answers its rows under `data`.** `meta.total` is the rows the list matched before paging, everywhere.
- **A sum over a top-N has a name of its own** (`frame_count`, `failed_count`, `resource_count`, `size_bytes`, `beacon_count`), so it is never read as the row count.
- All twenty analytics responses carry the two objects, including `POST /analytics/query` and `POST /analytics/histogram`.

</ChangelogEntry>

<ChangelogEntry date="2026-09-20" type="removed" area="api" title="The deprecated API names no longer answer">

228 of them, across analytics, synthetic, notifications, applications, issues and partners. Each had a replacement served since the release that deprecated it, and each is out of the OpenAPI document, so a generated client stops offering it.

- **A request that still sends an old body key is refused.** A stale `id`, `bucket`, `first_party`, `range_days` or `mute_until` is a 422 naming the key, rather than a write that vanishes.
- **The usage window keeps its old names for two more releases.** `period_start`, `period_end` and `total_beacons` on `GET /organizations/{org_id}/usage` and on the partner usage route still answer, because `usage:read` is a customer scope.
- **The application keeps six flat fields** for the Shopware plugin: `source_hash`, `collector_hash`, `proxy_secret`, `collector_mode`, `collector_endpoint` and `pagetype_ruleset`.

</ChangelogEntry>

- **The checkout chart counts the Shopify checkout.** The stage counts come from the checkout events as well as the page URLs, so the chart agrees with the funnel card below it instead of sitting empty above it.

- **A step that comes out above the one before it explains itself.** On Shopify that is routine: a buyer who goes straight into the checkout never loads a cart page.
- A funnel grouped by session says why its checkout half is missing, because the pixel events carry no session id. Rotating an application's hashes now warns that it breaks an installed pixel.
- Fixed: the measured conversion rate on the business page was never shown. It read a field the API had renamed, so the page fell back to its estimate even for a shop whose funnel was reporting.

<ChangelogEntry date="2026-09-19" type="removed" area="api" title="The application's flat fields are gone">

The flat twins of the grouped settings no longer answer. Read them from `collection`, `shop.checkout`, `page_type`, `script`, `site_defaults` and `collector.proxy_secret`, which have carried the same values since 2026.9.27.

- **Removed**: `collect_sessions`, `collect_fetch_xhr`, `collect_error_messages`, `collect_error_frames`, `collect_query_keys`, `collect_query_values_for`, `session_consent`, `template_url_ids`, `checkout_tracking`, the three checkout path lists, `pagetype_rules`, `source_version`, `data_retention_days`, `store_stitch`, `count_visitors_by` and the two proxy-secret fields.
- **Create and update reject any key they do not know.** A removed flat field is a 422 naming it, so a settings write is never dropped in silence.
- **That covers read-only fields echoed back from a GET**, such as `id`, `source_hash`, `site_count` or `created_at`. A read-modify-write client has to send only the fields it changes.
- **The Shopware plugin is unaffected.** Its six fields stay flat, and sending `collector_mode` and `collector_endpoint` flat or under `collector` are both still accepted.

Docs: [Applications → Application fields](/en/concepts/applications#application-fields).

</ChangelogEntry>

<ChangelogEntry date="2026-09-19" type="new" area="api" title="The Shopify checkout reaches visitors, journeys and a stage trend">

- **The site status reports checkout events**, so a pasted pixel becomes visible. `events_today`, `last_event_at` and `events_available` sit beside the beacon fields, and a non-null `last_event_at` proves the pixel reports.
- **A visitor's journey carries the checkout.** `POST /analytics/visitors/detail` answers `events` beside `pages`, with the name, the funnel stage, the source and the time of each. Interleave the two arrays by time.
- **The visitors filter finds a Shopify buyer.** `contains_checkout_stage` counts a checkout event as reaching the stage. Each row is still a pageview row, so a visitor known only from events has none to list.
- **New `POST /analytics/funnels/checkout/stages`** reports the visitors who reached cart, checkout or success per hour or day, events included. A `compare_to` reaching behind the day the pixel was installed shows the installation as a rise.
- **New `POST /analytics/events`** lists the events themselves, newest first and cursor paginated, so a test order can be held against the Shopify order list. A filter with no column on the events table is a 422 naming it.

Docs: [Checkout funnel → API](/en/checkout-funnel#api).

</ChangelogEntry>

<ChangelogEntry date="2026-09-19" type="new" area="tracker" title="The Shopify checkout reports its own steps">

Shopify runs its checkout on its own infrastructure, where your theme script never loads, so the funnel ended at the cart.

- **Paste one snippet** in the Shopify admin, under Settings → Customer events → Add custom pixel. It reports three steps: checkout entered, payment submitted, order placed.
- **The dashboard links to the guide** with your application's hashes in the URL, so the snippet there is ready to paste.
- **On a first-party collector the pixel is first-party too.** The script loads from your own host, so the checkout makes no third-party request. Your proxy has to relay `/s/e/*` and `/c/e/*`.
- **It measures nothing else.** No Web Vitals, no page load and no errors come from the Shopify checkout.
- **An event carries** the step, the visitor's country, device, browser and traffic class, and the edge identifier. No URL, no session id, no order value, nothing Shopify knows about the customer.
- **[`store_stitch`](/en/tracker#store-stitch) has to be on.** Without the edge identifier the checkout numbers stay empty.
- **Set Permission to "Not required" and Data sale to "does not qualify".** On Shopify's defaults the pixel waits for marketing consent, and the two halves of your funnel then cover different populations.
- **Rotating the application's hashes stops the events.** The old script URL answers 404 silently, so paste the new snippet after a rotation.
- **Content blockers stop the pixel.** EasyList's EasyPrivacy list blocks Shopify's custom-pixel sandbox path, and uBlock Origin ships it by default. Those visitors send storefront pageviews and no checkout events.
- **Purchases are a lower bound.** Shopify does not fire its checkout completed event for most Shop Pay and Apple Pay orders.

Docs: [Track the Shopify checkout](/en/guides/shopify-checkout).

</ChangelogEntry>

<ChangelogEntry date="2026-09-19" type="changed" area="api" title="The checkout funnel counts Shopify checkout events">

The funnel reads the pixel's events beside the pageviews, which moves a few numbers for a Shopify shop.

- **An order reaches `success` and an entered checkout reaches `checkout`**, with no pageview on either. Visitors seen only in the checkout join `visitors_total`, so the conversion rate stays at or below 100 %.
- **New `payment_submitted_visitors`**: visitors who submitted payment, a fact beside the steps rather than a step. It is absent, not 0, where no event was read.
- **Payment without a success most likely means a wallet order.** That is what makes the success step a lower bound.
- **A cart to checkout rate above 100 % is normal now.** A buyer who went straight into the checkout never loaded a cart page, and step rates stay unclamped.
- **A filter the event rows cannot answer leaves them out**: URL, page type, campaign, a metric threshold.
- **The cohort comparison counts only visitors with a pageview.** A buyer whose whole run is checkout events shows in the success step and in no cohort.
- The sessions explorer, the session detail and the journey view still read the stage off pageviews.

Docs: [Checkout funnel → Shopify](/en/checkout-funnel#shopify).

</ChangelogEntry>

<ChangelogEntry date="2026-09-19" type="changed" area="dashboard" title="One word per thing">

The same number went by several names, in both languages. Every concept has one word now.

- **A page load is a pageview, a person is a visitor.** The dashboard also said page views, views, screen views, visits and unique visitors.
- **Labels that named the wrong number are corrected.** "Views per visit" divided pageviews by visitors and is now "Pageviews per visitor".
- **German tells a Site from a page.** A Site stays a Seite; a page in a list, a column or a count is a URL.
- **One rating scale**: Good / Needs improvement / Poor, in German Gut / Verbesserungswürdig / Schlecht.
- **One word for the measured span.** It is a period, not a window or a range.
- **Labels are sentence case.** Product and spec names keep their capitals: Core Web Vitals, Largest Contentful Paint, Speed Index, Service Worker, Early Hints, Best Practices.
- Empty charts say "No data in the selected period". The old wording named visitors on charts that do not count them.

</ChangelogEntry>

<ChangelogEntry date="2026-09-18" type="changed" area="dashboard" title="The error list groups a fault's variants into one row">

One broken script used to fill four of the top five rows. Browsers report the same place in the code a few characters apart, and a second caller is a second stack.

- **A row is a fault, not a signature.** It counts every variant and says how many signatures it stands for.
- **"New", "Rising", the sparkline and the affected pageviews cover the whole group.** A row no longer reads as new when its biggest signature changed.
- **A signature's page switches between the variants of its fault.** Stored fingerprints do not change and nothing regroups.
- **`POST /analytics/error-types` takes `group_variants`**, off by default. A grouped row carries the summed count and lists every fingerprint in `variants`.
- **Match rows across periods by their variants.** The row's own `fingerprint` is its biggest variant and can change.

Docs: [Analytics → Error Analytics](/en/analytics#error-analytics).

</ChangelogEntry>

<ChangelogEntry date="2026-09-18" type="new" area="api" title="An application says what it runs on">

An application now records its platform, whether it is a shop and whether it is a single-page app.

- **`platform`** holds the shop system or CMS, for example Shopware 6, Shopify or PrestaShop. The last two could not be stored before, having no body-class ruleset.
- **A platform you set is `manual`**, and later detection leaves it alone. The object carries `key`, `source`, `detected_via` and `detected_at`.
- **The body-class page-type read is its own switch**, `page_type.body_class`. Picking a platform does not turn it on, and `pagetype_ruleset` is derived from the two.
- **`shop.active`** says whether an application is a shop, with `shop.source` for where that came from. Without a setting it follows the platform.
- **`spa`** marks a single-page app, set by hand and off by default. Nothing reads either flag yet.
- **The response groups its fields**: `page_type`, `shop.checkout`, `collection`, `collector`, `script` and `site_defaults`. Create and update take the same groups as partial objects.
- **The flat fields are deprecated.** They still work, and an API client should move to the groups.
- **Saving from the dashboard sends only what you changed.**

Docs: [Applications → Application fields](/en/concepts/applications#application-fields).

</ChangelogEntry>

<ChangelogEntry date="2026-09-18" type="new" area="platform" title="Shopify pageviews get a page type from the URL">

A soft navigation carries no document header, and Safari before 16.4 does not expose one. Those Shopify pageviews had no page type at all, and the collector now reads it from the URL. The label is Shopify's own (`product`, `collection`, `page`, `index`, `cart`, `search`, `blog`, `article`), the same one a hard load reports. Rows already stored stay empty.

Docs: [Server-Timing → Page type](/en/guides/server-timing#page-type).

<ChangelogEntry date="2026-09-18" type="changed" area="tracker" title="A repeated fetch/XHR failure sends one beacon">

The tracker sends a `fetch_xhr_update` for the first failure with a given status on an endpoint. Repeats only raise the error count, which the next beacon carries anyway. A polled endpoint that an ad blocker rejects used to cost up to 20 collector requests per pageview.

</ChangelogEntry>

<ChangelogEntry date="2026-09-18" type="fixed" area="tracker" title="A script the browser cannot parse is one error group">

Only Firefox's wording was recognized as `syntax_unexpected_token`, so the same broken script showed up once per engine. Chrome and Safari now get the same kind and the readable sentence with it. The affected `SyntaxError` groups get a new fingerprint and appear as new once. Where a site stores no messages the kind comes from the tracker, so old groups keep growing until browsers fetch the new bundle.

Docs: [Tracker → What a message says](/en/tracker#message-shape).

</ChangelogEntry>

<ChangelogEntry date="2026-09-17" type="changed" area="api" title="The checkout funnel reports a real conversion rate">

The rate showed anything from 30 % to 130 %. It divided by the cart step, which a drawer cart, an express checkout or a deep link never produces.

- **The conversion rate divides buyers by all visitors.** That is the number GA4 and Shopify report, against the usual 1 to 3 % benchmark.
- **`visitors_total` sits beside it**, and every point of the series carries its own `visitors`. Bucket visitors do not add up to the window total.
- **`FunnelStep.conversion_rate` is now `reach_rate`.** Same number, honest name: the share of the first step, which can exceed 100 %.
- **A conversion rate per time bucket**, measured against that bucket's own first step. The series has a point for every bucket with traffic, so a broken day reads 0 %.
- **New `POST /analytics/funnels/checkout/cohorts`** compares visitors with an observed success against those who reached the checkout without one. Per group: Web Vitals over the journey and per stage, cart calls, their latency and their failures.
- **`checkout_no_success` is not a count of lost purchases.** A real buyer lands in it whenever the success page is invisible to the tracker.
- **Four more numbers**: `cart_interaction_rate` (benchmark 5 to 6 %), `cart_interaction_error_visitors`, `time_to_success_seconds` (p50, p75, p90) and cart interaction kinds per point.
- **Read the first two as floors** wherever the shop's cart calls are invisible to fetch/XHR collection.
- **Filters that pick funnel pages no longer narrow the denominator** (`checkout_stage`, the cart thresholds). Audience filters (site, country, device, campaign) narrow both halves.
- **A visitor count that times out leaves `visitors_total` and `conversion_rate` out** of the response. A rate that could not be measured is absent, never 0 %.

Docs: [Checkout funnel → What the numbers mean](/en/checkout-funnel#what-the-numbers-mean).

</ChangelogEntry>

<ChangelogEntry date="2026-09-14" type="new" area="api" title="Which API calls fail where an error fires">

Built for the rejection that carries no message and no stack: the error says nothing, the failing request says which URL, method and status.

- **`POST /analytics/error-types/correlated-requests`** asks an error signature which fetch/XHR endpoints fail in the same pageviews.
- **Every endpoint comes with the share it fails at in pageviews without that error.** The list is ranked by the ratio of the two.
- **The answer says endpoints occur together, never that one caused the other.**
- **Which failures count follows the error's message.** An empty-response error matches cancelled calls, an invalid-JSON error matches 4xx and 5xx pages.
- **Applications with fetch/XHR collection off are left out** rather than blanking the answer, and `fetch_xhr_collected: false` says so.
- **It reads raw pageviews**, so it goes back as far as those are kept, not as far as the rollups.

Docs: [Analytics → What broke, and where](/en/analytics#error-detail).

</ChangelogEntry>

<ChangelogEntry date="2026-09-14" type="fixed" area="platform" title="Fewer nameless API calls in a pageview">

A page with more than 24 API endpoints keeps 24 of them named instead of 23.

- **The tracker's own overflow row no longer takes a slot.** It sums up dozens of calls, so it always won the contest for the last one.
- **Failures of a displaced third-party endpoint move back to the third-party column.** They were counted as the site's own.
- **Ad-blocked calls in the nameless `other` row no longer count as failures.** A busy page with blocked tracker calls reports a slightly lower fetch/XHR error rate.
- Pageviews collected before the deploy keep the shape they were collected in.

</ChangelogEntry>

<ChangelogEntry date="2026-09-13" type="changed" area="tracker" title="Readable placeholders in error messages">

- **A stripped literal keeps its quotes.** A sample reads `'*' is not a valid selector`, a removed email reads `<email>`, and numbers keep the bare `*`.
- **A URL in a message survives as origin plus path.** Query, fragment and numeric path IDs are still removed.
- **Safari selector errors carry their shape again.** WebKit's `'x' is not a valid selector` arrived unclassified, so the same fault grouped separately per engine.
- **New occurrences classify as `selector_invalid`**, name the selector in `message_value` and share one fingerprint across engines.
- **Error groups built on message text restart once.** Errors with a recognized shape keep their fingerprint; unclassified ones regroup with the tracker rollout.

Docs: [Tracker → What a message says](/en/tracker#message-shape).

</ChangelogEntry>

<ChangelogEntry date="2026-09-13" type="fixed" area="tracker" title="Error counts stop at 1000 per pageview">

One visitor stuck in a recursion loop used to report hundreds of thousands of errors.

- **The tracker stops counting at 1000 per channel**, errors and failed resources separately. The collector clamps beacons from older builds to the same ceiling.
- **A stored count of exactly 1000 means "1000 or more"**, and the dashboard writes it as "at least".
- **A breakdown never exceeds the number it breaks down.** Where a beacon reports more occurrences than the cap, its signatures are scaled into the stored total.
- **Past the cap the tracker records no signature it has not seen yet.** An error that first occurs after a storm of 1000 others can be missing from the list.
- **An error the tracker could not record no longer inflates the count.** A revoked Proxy or a throwing `toString` used to bump the count and lose its entry; it lands as "Other" now.

Docs: [Tracker → What counts as an error](/en/tracker#what-counts).

</ChangelogEntry>

<ChangelogEntry date="2026-09-13" type="changed" area="dashboard" title="Every error has its own page">

Opening an error used to expand a row inside a table inside a card, with the stack, the breakdowns and the samples in one table cell.

- **A signature lives at `/org/<org>/errors/<fingerprint>`**, which is also its share link. Existing `?error=` links redirect there.
- **The list leads with what broke, in a sentence**: what happened, whose code it is, the file, how often it occurred and when it last did.

<ChangelogEntry date="2026-09-04" type="new" area="api" title="How old the cache hit was, per tier">

The cache status says whether the visitor got a cached object. Two new `Server-Timing` keys say how old it was, which is the other half of the question: a shop with a 95 percent hit rate whose objects average four hours old is serving fast and stale.

- **`fm-cdn-age;desc=42` fills `cdn_age`, `fm-origin-age;desc=312` fills `origin_age`**, both in seconds. Emit them on a cache hit only, because on a miss the age is 0 and drags every percentile down. The value rides `desc`, not `dur`: `dur` is specified in milliseconds and DevTools draws it as a bar in the document request's timing view, so an age there would render as a backend phase that never happened. Values above a year are dropped rather than clamped, since a number that large is a timestamp.

The origin's header freezes inside the CDN object, so under a CDN hit the origin value is the age at the moment the CDN fetched, and only the sum is the age the visitor saw. The Server-Timing panel reports three rows, `cdn`, `origin` and `content` (the sum under a CDN hit), computed server-side because the p75 of a sum is not the sum of the p75s.
- Both are metrics with the usual avg and p50 to p99, fields on the beacon rows and in the pageview detail next to the cache status they qualify, and available through the MCP server's `get_server_timing`.
- **`fm-fpc` is renamed to `fm-origin-cache`** and the old name is no longer recognized. It was the only first-party key calling the origin tier something other than `origin`, which next to `fm-origin-age` would have put two words for one tier in a single header. <ChangelogEntry date="2026-07-15" type="fixed" area="tracker" title="No duplicate mid-pageview update beacons">

On a page that logged both an error and a fetch/XHR call, the tracker could fire two byte-identical update beacons at the same instant: the error channel and the fetch/XHR channel each tracked their own send timer, and neither knew the other had already shipped the full snapshot. Because every beacon carries the complete cumulative state, the second one was pure duplication. The tracker now tracks unsent activity per channel and skips an update once the current state is already on the wire. Fewer requests, and no data lost: the update that does go out still carries both channels.
