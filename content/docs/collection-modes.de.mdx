Jede Fastmon-Application hat ein **Erfassungs-Preset**. Es legt fest, was
der Tracker im Browser des Besuchers erfasst und wie viel davon behalten
wird. Eine Einstellung an der Application; jederzeit umschaltbar, das
ausgelieferte Script aktualisiert sich automatisch — kein Redeploy, keine
Tag-Änderung.

Drei Presets: `minimal`, `standard`, `full`. Default ist `standard`, und
für fast alle ist das genau richtig. Ein Preset ist nur eine Abkürzung:
Es entfaltet sich in eine Handvoll Einzeleinstellungen (siehe
[Feinjustierung](#feinjustierung-die-einzelnen-einstellungen)), du kannst
also von einem Preset ausgehen und ein Flag ändern — die App
kennzeichnet das Ergebnis dann als `custom`.

## Vergleich auf einen Blick

|                                   | `minimal`                       | `standard` (Default)                     | `full`                          |
| --------------------------------- | ------------------------------- | ---------------------------------------- | ------------------------------- |
| Web Vitals                        | ✓                               | ✓                                        | ✓                               |
| Unique Visitors                   | ✗                               | ✓ (am Edge abgeleiteter `stitch`)        | ✓                               |
| Seitenübergreifende Sessions      | ✗                               | ✗                                        | ✓                               |
| Storage auf dem Besucher-Gerät    | Keiner                          | Keiner                                   | `sessionStorage`-Session-ID     |
| Query-Parameter der Seiten-URL    | Entfernt                        | Key-Namen behalten, Werte verworfen      | Key-Namen behalten, Werte verworfen |
| Fehler                            | Typ + Count, nur Frame-Hosts    | + volle Stack-Frames (Host, Pfad, Zeile/Spalte) | + die Fehler-Message     |
| fetch/XHR-Endpoint-Timing         | ✗                               | ✓                                        | ✓                               |
| Consent-Gate für die Session-ID   | —                               | —                                        | Standardmäßig keins (Schreiben beim Load) |
| Wann wählen                       | So schlank wie möglich; gar kein Besucher-Identifier | Fast alle           | Session-Analytics oder interne Apps |

Jedes Preset teilt dieselbe Datenschutz-Untergrenze: keine Cookies, keine
IP-Speicherung, kein roher User-Agent, kein Fingerprinting. Siehe
[Privacy](/de/privacy).

## `standard`: der Default

Auf `standard` startet jede neue Application, und für fast jede
öffentliche Website ist es die richtige Wahl.

Du bekommst Web Vitals, Fehlerdiagnose mit vollen Stack-Frames (aber
nicht die freie Fehler-Message), fetch/XHR-Endpoint-Timing und
**Unique-Visitor-Zahlen** — und das alles, ohne etwas auf dem Gerät des
Besuchers zu speichern.

Unique Visitors kommen aus dem **`stitch`**: einer pseudonymen ID, die
der Fastmon-Edge aus der Anfrage (IP und User-Agent) ableitet, nie aus
dem Client. Das Salt rotiert etwa täglich und liegt nur im Edge-Speicher,
die Verknüpfbarkeit ist also auf ≤24 h mit Forward Secrecy gedeckelt, und
im Browser wird nichts gespeichert. Siehe
[der am Edge abgeleitete `stitch`](/de/privacy#der-am-edge-abgeleitete-stitch-identifier).

Was `standard` **nicht** tut:

- auf das Gerät des Besuchers schreiben (keine Cookies, kein
  `localStorage` / `sessionStorage`),
- eine seitenübergreifende Session-ID mitführen (das ist `full`),
- Fehler-**Message**-Text behalten (nur Typ, Count und Stack-Frames),
- Query-Parameter-**Werte** behalten (die Key-Namen bleiben; Werte werden
  verworfen, außer der Key steht auf der Allow-List).

**Passt für dich, wenn:** du eine öffentliche Site betreibst und echte
Diagnose plus Besucherzahlen mit der einfachsten Ausgangslage willst — für
unseren Beacon keine Cookies und kein Geräte-Storage.

## `minimal`: das Schlankste

`minimal` schaltet jede optionale Einstellung aus. Du bekommst die
Kern-Web-Vitals und Fehler-Typ + -Count (nur Frame-Hosts, keine Pfade,
keine Message) — und nichts, was einen Besucher identifiziert.

Weil es auch den `stitch` verwirft, hat **`minimal` gar keine
Unique-Visitor-Metrik**: Diese Zahlen lesen sich als nicht messbar
(leer), nicht als null. Query-Strings werden komplett entfernt
(`/p?a=1#x` → `/p`), es gibt kein fetch/XHR-Timing und keinen
Geräte-Storage.

**Passt für dich, wenn:** du den absolut schlanksten Fußabdruck willst
und keine Besucherzahlen oder Per-Endpoint-Timing brauchst — die
strengste Position, oder eine Site, wo selbst eine gedeckelte pseudonyme
ID mehr ist als gewollt.

## `full`: Sessions und Detailtiefe

`full` behält alles, was `standard` erfasst, und ergänzt:

- eine **seitenübergreifende Session-ID**, sodass Pageviews zu einer
  Session verknüpft werden (Journeys, Funnels, Wiederkehrer-Metriken).
  Es ist das Einzige, was aufs Gerät geschrieben wird —
  `sessionStorage["_fms"]`, das mit dem Tab stirbt. Aktiviert über
  `collect_sessions`.
- die **Fehler-Message** (läuft weiterhin durch den PII-Scrubber, bevor
  sie den Browser verlässt), zusätzlich zu den Stack-Frames, die
  `standard` schon behält.

`full` liefert die Session-ID **beim Pageload** geschrieben aus — ohne
Consent-Gate im Standard (`session_consent` steht auf `immediate`).
Wenn du die Session-ID zurückhalten willst, bis ein Consent-Manager sie
erlaubt, siehe
[Die Session-ID hinter Consent gaten](#die-session-id-hinter-consent-gaten).

**Passt für dich, wenn:** du Session-Analytics willst, oder rein intern
misst (Intranet, Employee-App), wo Besucherkreis und Consent-Kontext
anders aussehen, oder du eine Rechtsgrundlage hast, die einen
seitenübergreifenden Identifier abdeckt.

Im Zweifel bleib bei `standard`. Eine seitenübergreifende Session-ID ist
ein größerer Datenschutz-Schritt; geh ihn nur, wenn du brauchst, was sie
bringt.

## Die Session-ID hinter Consent gaten

Keines der drei Presets wartet auf Consent — `standard` speichert gar
keine Session-ID, und `full` schreibt sie beim Load. Wenn du Sessions
speicherst **und** die Session-ID zurückhalten musst, bis dein
Consent-Manager (CMP) sie erlaubt, ist das eine **Custom**-Konfiguration:
`collect_sessions` an lassen, aber `session_consent` auf `deferred` setzen.

Mit dieser Kombination verzögert das ausgelieferte Script den einen
Geräte-Write (`sessionStorage["_fms"]`), bis dein CMP aufruft:

```js
// Im "Akzeptieren"-Handler deines Cookie-Banners:
window.fastmon.grantConsent();
```

`grantConsent()` schreibt nur und ist idempotent; ruf es auf, sobald
Consent erteilt ist. Es gibt keinen Widerruf-Call — vor dem Consent wurde
nichts geschrieben, es gibt also nichts zu löschen.

Zwei Dinge, die es genau zu treffen gilt:

- Das gated **nur den Session-ID-Write auf dem Gerät**, nicht die
  Erhebung. Beacons gehen auch vor dem Consent raus — Web Vitals, Fehler,
  der Unique-Visitor-`stitch` — nur mit leerer Session-ID. Consent
  schaltet seitenübergreifende **Verknüpfbarkeit** frei, keine neuen
  Datenkategorien.
- Ohne `collect_sessions` gibt es nichts zu gaten: Das Bundle fasst den
  Storage nie an, Consent ist also gegenstandslos.

(Ein älterer `window.__fastmon_consent()`-Call existiert noch als
deprecated Alias, aber bevorzuge `grantConsent()`.)

## Feinjustierung: die einzelnen Einstellungen

Ein Preset setzt nur die folgenden Flags; du kannst sie auch einzeln
setzen, dann kennzeichnet die App das Ergebnis als `custom`.

- **`collect_sessions`** (nur `full`) — die `sessionStorage`-Session-ID für
  seitenübergreifende Sessions. Die einzige Einstellung, die aufs Gerät
  schreibt.
- **`store_stitch`** (`standard`, `full`) — den am Edge abgeleiteten
  Besucher-`stitch` behalten. Aus macht die gespeicherte Zeile echt
  anonym, auf Kosten der Unique-Visitor-Zahlen. Geräte-Storage so oder
  so keiner.
- **`session_consent`** — `deferred` verzögert den Session-ID-Write bis
  `grantConsent()`; `immediate` schreibt beim Load. Nur relevant, wenn
  `collect_sessions` an ist.
- **`collect_query_keys`** (`standard`, `full`) — Query-Parameter-Key-Namen
  behalten (Werte weiterhin verworfen, außer Allow-List-Keys). Aus
  entfernt den ganzen Query-String.
- **`collect_error_frames`** (`standard`, `full`) — volle Stack-Frames
  behalten (Host, Pfad, Zeile/Spalte). Aus kollabiert Frames auf ihren
  Host.
- **`collect_error_messages`** (nur `full`) — die freie Fehler-Message
  behalten (PII-gescrubbt). Getrennt vom Frame-Detail.
- **`collect_fetch_xhr`** (`standard`, `full`) — fetch/XHR-Endpoint-Timing
  und -Fehler erfassen.

Die Begründung hinter den Identifier-Schaltern steht unter
[Privacy → Identifier ganz abschalten](/de/privacy#identifier-ganz-abschalten).

## Preset wechseln

Application in Fastmon öffnen, zu den Erfassungseinstellungen gehen und
ein anderes Preset wählen (oder die Einzeleinstellungen anpassen). Die
Änderung greift, sobald der Script-Cache rolliert — für aktive Besucher
meist binnen Minuten, für neue sofort. Du musst weder redeployen noch das
`<script>`-Tag anpassen.
